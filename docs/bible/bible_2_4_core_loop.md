## 4.1. Что такое Core Loop и почему это важно

Core Loop — это минимально значимый цикл игровой активности, который приносит удовольствие и мотивирует продолжать. Это «сердцебиение» игры: повторяющийся паттерн действий, который игрок выполняет снова и снова, и каждый цикл приносит ему награду — удовольствие, прогресс или новый вызов. Если механика — скелет игры, а динамика — её дыхание, то Core Loop — это её пульс.

Концепция Core Loop пронизывает всю литературу по геймдизайну, хотя и под разными названиями: «игровой цикл» (game loop), «петля опыта» (experience loop), «кор-геймплей» (core gameplay), «30 секунд веселья» (30 seconds of fun). Разные авторы подчёркивают разные аспекты, но сходятся в главном: **игра — это не набор механик, а цикл; и качество этого цикла определяет качество игры**.

Критическое различие, которое проводит Зубек (Кн. 6): **Core Loop ≠ микроцикл**. Самый быстрый цикл не обязательно является самым весёлым. В The Sims микроцикл (есть, спать) — это рутина, поддерживающая персонажа; Core Loop — пойти на работу → заработать → купить вещи → улучшить жизнь → повторить. Микроцикл обслуживает персонажа; Core Loop обслуживает *мотивацию игрока*. Это различие фундаментально: оптимизировать неправильный цикл — всё равно что полировать педали в автомобиле, у которого не работает двигатель.

Для AI-системы Gidede Core Loop — это **основной конструктивный элемент** генерации. Прежде чем проектировать механики, экономику, прогрессию или нарратив, AI должен определить Core Loop: что игрок *делает* снова и снова, и *почему* ему это нравится. Все остальные элементы игры выстраиваются вокруг Core Loop, поддерживая и обогащая его.

## 4.2. Анатомия Core Loop: петля взаимодействия

### 4.2.1. Базовая петля взаимодействия (Кук, через Фуллертон)

Дэниел Кук (через Фуллертон, Кн. 5) формализует минимальную единицу взаимодействия как **петлю взаимодействия** (interaction loop):

```
Ментальная модель → Решение → Действие → Правила → Фидбэк → Обновление модели
```

Каждая итерация этой петли — один акт взаимодействия игрока с игрой. Петля *когнитивна* прежде, чем механична: игрок формирует намерение (ментальная модель), принимает решение, действует, наблюдает результат, обновляет понимание. Петля замкнута, когда игрок может действовать, видеть результат и учиться на нём. Незамкнутая петля — это фрустрация: «я делаю что-то, но не понимаю, что происходит».

### 4.2.2. Цепочка навыков (Skill Chain, Кук)

Петли взаимодействия вкладываются друг в друга, образуя **цепочку навыков** (skill chain):

```
Микро-петля (нажать кнопку → атака)
  → Мезо-петля (убить врага → получить лут)
    → Макро-петля (пройти подземелье → повысить уровень)
      → Мета-петля (завершить игру → открыть новый режим)
```

Каждый уровень вкладывается в следующий: результаты микро-петли питают мезо-петлю, результаты мезо — макро, и так далее. Ключевой вопрос валидации: есть ли обратная связь на *каждом* уровне? Соединены ли уровни? Если микро-петля не связана с мезо-петлёй (например, бой не даёт лута), цикл рвётся — и игрок теряет мотивацию.

### 4.2.3. Пять геймплейных циклов Зубека

Зубек (Кн. 6) описывает пять концентрических циклов с разной периодичностью:

| Уровень | Длительность | Пример действий |
|---------|-------------|-----------------|
| **Микро** | Секунды | Двигаться, атаковать, поднять предмет |
| **Малый** | 1-2 минуты | Найти врагов → сражение → сбор лута |
| **Средний** | 5-10 минут | Экспедиция → зачистка → возврат → продажа |
| **Крупный** | 15-30 минут | Зачистить зону, сменить команду, прокачать навыки |
| **Макро** | Часы | Завершить регион, продвинуть сюжет |

Зубек визуализирует это как **«луковую» диаграмму** (concentric schema) — вложенные кольца, где самый быстрый цикл в центре, самый медленный — на периферии. Это одновременно коммуникационный и диагностический инструмент: пробелы в диаграмме = пробелы в дизайне. Если у игры есть микро- и макро-циклы, но нет среднего — игрок будет дезориентирован между «что делать прямо сейчас» и «к чему это всё ведёт».

Принцип расширения от Core Loop: (1) начать с микро-уровня и протестировать фундамент; (2) итеративно найти Core Loop; (3) добавлять более крупные циклы — они должны *поддерживать* меньшие (результаты макро-цикла питают выбор в микро-цикле).

## 4.3. Шесть временных масштабов интерактивной петли

Селлерс (Кн. 13) расширяет модель петли взаимодействия, выделяя шесть временных масштабов, на которых работает интерактивная петля:

| Масштаб | Длительность | Тип вовлечения |
|---------|-------------|----------------|
| **Action/Feedback** | мс–с | Рефлексивное внимание, моментальный геймплей |
| **Short-term Cognitive** | с–мин | Тактические решения |
| **Long-term Cognitive** | мин–ч | Стратегические решения |
| **Social** | ч–дни | Социальные взаимодействия |
| **Emotional** | ч–недели | Эмоциональная привязанность |
| **Cultural** | недели–месяцы | Культурная идентификация с игрой |

Петли **наслаиваются**: быстрые внутри медленных. «30 секунд веселья» из Halo — это 3-секундная петля внутри 30-секундной внутри 5-минутной внутри 20-минутной. Каждый масштаб обслуживает разные когнитивные и эмоциональные потребности: рефлексы на микро-уровне, тактика на мезо-уровне, стратегия на макро-уровне, социальная идентичность на мета-уровне.

**Интерактивный бюджет** (Селлерс) — важное ограничение: каждый человек имеет ограниченную способность к интеракции. Слишком много интерактивности = когнитивная перегрузка; слишком мало = скука. Дизайнер должен управлять когнитивной нагрузкой одновременно на всех вложенных петлях. Это особенно критично для Core Loop: если базовая петля перегружена (слишком много решений за слишком короткое время), игрок не сможет войти в состояние потока.

## 4.4. Три структурных типа Core Loop

Селлерс (Кн. 13) предлагает типологию игровых систем, которая одновременно является типологией Core Loop. Каждая игра имеет доминирующий тип Core Loop, хотя реальные игры комбинируют все три:

### 4.4.1. Двигатель (Engine) — однонаправленный ресурсный поток

**Структура**: Усиливающая или балансирующая петля с одним ресурсом. Игрок вкладывает ресурс → получает больше ресурса → вкладывает ещё → получает ещё больше (или тормозящая версия: тратит ресурс для предотвращения runaway).

**Boosting Engine** (усиливающий): Добавляет ресурсы в игру, создавая рост. Игрок выбирает: потратить ресурс сейчас или инвестировать для увеличенного будущего потока. Пример: Монополия — деньги → недвижимость → больше денег. Dominion — карта → ресурсы → лучшая карта → больше ресурсов.

**Braking Engine** (тормозящий): Удаляет ресурсы из игры, предотвращая runaway. Пример: налоги, износ оружия, расход маны, затрата действий.

**Три патологии двигателей**:

1. **Runaway** (саморазгон): Усиливающий двигатель без тормозящего. «Богатые богатеют» — игрок, получивший раннее преимущество, экспоненциально отрывается. Диагностика: усиливающий двигатель без тормозящего = runaway. Решение: добавить тормозящий двигатель.

2. **Deadlock** (тупик): Ресурс цикла нужен для запуска самого цикла. Конструктор, для работы которого нужны детали, которые производит этот же конструктор. Решение: обеспечить начальный «затравочный» ресурс.

3. **Stall** (остановка): Недостаточно ресурсов для продолжения цикла. Производство слишком медленное по сравнению с потреблением. Решение: увеличить производство или уменьшить потребление.

### 4.4.2. Экономика (Economy) — конвертация ресурсов

**Структура**: Усиливающая петля с обменом/конвертацией ресурсов. Игрок обменивает один ресурс на другой с нелинейным приростом ценности.

**Ключевое свойство — развёртывание сложности** (unfolding complexity): экономика начинает просто (хлеб + дерево) и постепенно добавляет новые ресурсы и цепочки конвертации (руда → железо → сталь → оружие). Каждая новая валюта увеличивает глубину решений. Игрок начинает с тривиальных обменов и постепенно осваивает всё более сложные цепочки.

**Валюты** — каталитические ресурсы, которые не потребляются при обмене (золото, серебро), но подвержены инфляции (слишком много валюты = обесценивание) и стагнации (слишком мало оборота = бессмысленность).

**Пример RPG**: Убить монстра → получить опыт и золото → повысить уровень → стать сильнее → убить более сильного монстра → получить больше опыта и золота. Это экономика с встроенным двигателем: XP → уровень → способности → больше XP.

### 4.4.3. Экология (Ecology) — балансирующая конвертация

**Структура**: Балансирующая петля с обменом/конвертацией ресурсов. Целое стремится к **динамическому равновесию** (метастабильности), хотя части постоянно меняются.

**Метастабильность, а не стазис**: Здоровая экология — это не неподвижное равновесие, а динамическое. Подсистемы постоянно колеблются, но система в целом остаётся устойчивой. Пример: бой в RPG — два противника обмениваются ударами, HP каждого колеблется, но бой в целом имеет тенденцию к завершению (победа одного).

**Устойчивость (resilience) vs Хрупкость (brittleness)**: Устойчивая экология восстанавливается после возмущения (игрок потерял много HP, но использовал зелье и восстановил позицию). Хрупкая — разрушается (потеря HP → каскад неудач → смерть). Переход между устойчивостью и хрупкостью трудно обнаружить — система может казаться устойчивой, пока не столкнётся с определённым типом возмущения.

**Три типа экологий в играх**:

1. **Инвентарь**: Больше предметов → меньше места → давление освободить → баланс. Конфликт между «хранить на всякий случай» и «освободить для нового».

2. **Бой**: Два противника уравновешивают друг друга. HP как ресурс, который тратится и восстанавливается. Атака и защита как противоположные потоки.

3. **Социальная**: Трёхфракционная система — если одна фракция усиливается, две другие объединяются против неё (Dark Age of Camelot). Двухфракционные системы склонны к runaway: одна сторона начинает побеждать → привлекает больше игроков → побеждает ещё больше. **Три фракции — минимальное число для экологической стабильности**.

### 4.4.4. Комбинирование типов

Реальная игра — иерархия вложенных систем. RPG: экономика (ядро прокачки) + экология (бой) + двигатель (ресурсы) — все вложены друг в друга. Стратегия: несколько двигателей (добыча + производство) + экономика (торговля) + экология (баланс сил). Разные типы Core Loop требуют разных подходов к балансировке: двигатель — контроль runaway, экономика — контроль инфляции, экология — контроль хрупкости.

## 4.5. Цикл прогрессии: физика мотивации

Шрайбер (Кн. 7) формализует Core Loop через **цикл прогрессии** — базовую структуру, которая управляет темпом и мотивацией игрока:

### 4.5.1. Структура цикла прогрессии

```
Мотивация → Прогрессия → Награда → Удовлетворение
```

Каждый проход через этот цикл — один «шаг» прогрессии. Мотивация (почему игрок действует) → Прогрессия (движение к цели) → Награда (подтверждение прогресса) → Удовлетворение (позитивное подкрепление) → новая мотивация (следующий шаг).

### 4.5.2. Формальная динамика

Шрайбер описывает прогрессию через формальные переменные:

- **Скорость прогрессии** = 1 / сопротивление. Сопротивление — сумма всех факторов, замедляющих прогресс: сложность врагов, дефицит ресурсов, ограничения времени. Высокое сопротивление = медленная прогрессия; низкое = быстрая.

- **Ускорение прогрессии** = dv/dt. Когда ускорение положительное — игрок чувствует рост («я становлюсь сильнее!»). Когда ускорение становится отрицательным — игрок чувствует замедление и начинает рассматривать *выход из цикла* (сменить деятельность, бросить игру).

- **Отрицательное ускорение** — критический момент дизайна: именно здесь игрок решает, продолжать или нет. Дизайнер должен управлять ускорением, создавая «провалы» (отрицательное ускорение, за которым следует положительное — ощущение прорыва) и избегая «плато» (нулевое ускорение без просвета — ощущение застоя).

### 4.5.3. Эффект Зейгарник

Шрайбер ссылается на психологический феномен — **эффект Зейгарник**: незавершённые действия запоминаются лучше и вызывают тревогу, подталкивая к завершению. Это психологический двигатель, который удерживает игрока в Core Loop. В Civilization «ещё один ход» — это классический эффект Зейгарник: всегда есть незавершённое действие (строящееся здание, исследуемая технология, незахваченный город), и мозг тревожно сигнализирует: «Доведи до конца!»

Для AI-системы Gidede эффект Зейгарник — **конструктивный принцип**: Core Loop должен всегда содержать незавершённые под-циклы, создающие «тягу» к продолжению. Если все под-циклы завершены одновременно — мотивация падает, и игрок выходит из игры.

## 4.6. Конверсионные цепи и циклы (Зубек)

Зубек (Кн. 6) предлагает экономическую модель внутренней структуры Core Loop через **конверсионные цепи** — последовательности механик, преобразующих одни ресурсы в другие:

### 4.6.1. Конверсионные цепи

Механики игры образуют цепочки «производитель → потребитель»:

- **Бой** конвертирует монстров + здоровье → лут
- **Продажа** конвертирует лут → золото
- **Лечение** конвертирует золото → здоровье
- **Покупка** конвертирует золото → снаряжение
- **Снаряжение** конвертирует → эффективность боя → больше лута

Каждое звено цепи — одна механика. Цепочка в целом — один проход Core Loop.

### 4.6.2. Конверсионные циклы

Когда цепочка замыкается (последний ресурс конвертируется обратно в первый), образуется **конверсионный цикл** — повторяющийся Core Loop с анализируемыми свойствами:

**Прибыльный цикл** → линейный рост ресурсов → риск **гринда**. Если каждый проход через цикл приносит чистую прибыль, ресурсы растут линейно. Это предсказуемо и удовлетворяюще на ранних этапах, но со временем превращается в рутину — каждый проход одинаков, мотивация снижается.

**Убыточный цикл** → истощение ресурсов → риск **фрустрации**. Если каждый проход отнимает больше, чем даёт, ресурсы убывают. Это может создавать напряжение и значимость решений, но при затяжном убыточном цикле игрок теряет мотивацию.

**Динамическая настройка** — ключевой механизм: масштабирование кривой прибыльности во времени, так что цикл *переходит* от прибыльного к убыточному. На ранних этапах — прибыльный цикл (ощущение роста, мотивация продолжать). На поздних — убыточный (напряжение, необходимость оптимизации, выбор приоритетов). Этот переход — конкретный дизайнерский рычаг, предотвращающий и гринд, и фрустрацию.

### 4.6.3. Применение к RPG: макро-модель

Шрайбер (Кн. 7) формализует макро-модель RPG как систему вложенных циклов:

T часов → L уровней → L-1 переходов → ~L/T переходов/час → L/2 стадий контента → ≥3×(L/2) конфигураций противника

Каждый «переход» — один проход Core Loop, завершающийся повышением уровня. Каждая «стадия контента» — диапазон уровней с однотипными вызовами. Каждая «конфигурация противника» — уникальная комбинация врагов и механик. Формула показывает: для 40-часовой RPG с 20 уровнями нужно ≈30 конфигураций противника — астрономически меньше, чем если бы каждый бой был уникальным. Core Loop обеспечивает реиграбельность через вариацию контекста, а не уникальность каждого прохода.

## 4.7. Пять вопросов кор-геймплея (Гэри)

Джастин Гэри (Кн. 10) предлагает самый предписывающий фреймворк для определения Core Loop — пять вопросов, которые должен задать себе дизайнер:

### 4.7.1. Какой игровой цикл?

**Вопрос**: Можно ли описать Core Loop в 1-2 предложениях? Если нет — либо цикл не определён, либо он слишком сложен. Хороший Core Loop описывается просто: «Найди врагов → сразись → собери лут → улучшись → найди более сильных врагов». Если описание требует абзаца — дизайн, скорее всего, перегружен.

Этот вопрос заставляет дизайнера (или AI) **сформулировать суть игры** до того, как будут добавлены детали. Это как «elevator pitch» для Core Loop: если вы не можете объяснить его кратко, вы его не понимаете.

### 4.7.2. В чём главный конфликт?

**Вопрос**: Какое ограничение стоит на пути к цели? Конфликт — суть игры: без конфликта нет вызова, без вызова нет мотивации. Каждый дизайнерский вопрос должен проверяться: «служит ли это решение главному конфликту или подменяет его?»

Примеры главных конфликтов: Dark Souls — выживание в мире, который пытается вас убить. StarCraft — ограничение ресурсов при неограниченных амбициях. Portal — пространство, которое не позволяет пройти прямо. Главный конфликт определяет, какие механики *нужны*, а какие — лишние.

### 4.7.3. Какие ресурсы?

**Вопрос**: Какие ресурсы управляют Core Loop? Гэри выделяет три типа:

- **Масштабируемые** (Scalable) — растут со временем. Мана, золото, опыт. Управляют долгосрочной прогрессией.
- **Фиксированные** (Fixed) — неизменны. 1 действие за ход в настольной игре. Создают жёсткие ограничения и осмысленный выбор.
- **Накапливаемые** (Accumulating) — растут, если не используются. Эликсир в Clash Royale. Создают срочность: «потрать сейчас или дождись максимума, но упусти момент».

Тип ресурсов определяет динамику Core Loop: масштабируемые ресурсы порождают прогрессию, фиксированные — осмысленный выбор, накапливаемые — тайминг и срочность.

### 4.7.4. Как происходит взаимодействие?

**Вопрос**: Как игроки взаимодействуют друг с другом (или с игрой)? Пять типов:

- **Горячие общие ресурсы** (Hot shared resources) — видимый захват: «ты взял моё!». Пример:抢ление территорий в Risk.
- **Холодные общие ресурсы** (Cold shared resources) — скрытый выбор: «ты взял то, что я хотел, но я не вижу». Пример: драфт карт.
- **Прямой урон** — атака, разрушение, устранение. Пример: бой в Street Fighter.
- **Социальная дедукция** — блеф, скрытые роли, подозрение. Пример: Among Us, Werewolf.
- **Интеллектуальная дедукция** — логический вывод, анализ информации. Пример: шахматы, Mastermind.

Тип взаимодействия определяет *эмоциональный профиль* Core Loop: горячие ресурсы → агрессия и возмущение; холодные → обида и стратегия; прямой урон → адреналин; социальная дедукция → паранойя; интеллектуальная → удовлетворение от озарения.

### 4.7.5. В чём цель игры?

**Вопрос**: Как игра завершается? Три типа терминации:

- **Элиминация** — последний выживший побеждает. Пример: Battle Royale, Poker.
- **Ограничение по времени** — побеждает тот, кто достиг больше к моменту истечения. Пример: спортивные игры, раундовые соревнования.
- **Достижение цели** — первый достигший целевого состояния побеждает. Пример: гонки, квесты, сбор определённого количества очков.

Тип терминации определяет *структуру pacing*: элиминация → нарастающее напряжение (игроков всё меньше); ограничение по времени → пиковое напряжение в конце; достижение цели → рваный темп (кто-то может «выстрелить» в любой момент).

## 4.8. «30 секунд веселья»: Core Loop в действии

### 4.8.1. Происхождение концепции

Концепция «30 секунд веселья» приписывается Джейми Грисемеру, дизайнеру Halo (через Шрайбера, Кн. 7). Суть: базовый цикл боевого encounters в Halo занимает ~30 секунд и *сам по себе* является весёлым. Встретить врагов → выбрать подход → выполнить бой → оценить результат → повторить с вариацией. Весь Halo строится на вариации этого 30-секундного цикла: разные враги, разное оружие, разная тактика, но одна и та же базовая структура.

### 4.8.2. Вложенность петель в Halo

Селлерс (Кн. 13) разворачивает структуру Halo на вложенные петли:

- **3-секундная петля**: Прицелиться → выстрелить → попасть/промахнуться → скорректировать. Это рефлексивный уровень — чистый навык и реакция.
- **30-секундная петля**: Встретить группу врагов → выбрать тактику → выполнить серию боевых действий → зачистить область. Это тактический уровень — выбор подхода.
- **5-минутная петля**: Пройти секцию уровня → встретить новый тип врага → адаптировать тактику → достичь checkpoint. Это уровень вызова — нарастание сложности.
- **20-минутная петля**: Завершить уровень → увидеть кат-сцену → получить новый навык/оружие → начать следующий уровень. Это уровень прогрессии — рост и нарратив.

«30 секунд веселья» — это *минимальный* уровень, на котором Core Loop уже доставляет удовольствие. Не 3 секунды (слишком малы для осмысленного выбора) и не 5 минут (слишком долго для быстрой обратной связи). 30 секунд — золотая середина между действием и рефлексией.

### 4.8.3. Обобщение: нахождение «правильного» масштаба

Принцип «30 секунд веселья» обобщается: для каждой игры существует *оптимальный масштаб* Core Loop — минимальная длительность, при которой цикл уже приносит удовольствие. Этот масштаб зависит от жанра:

| Жанр | Оптимальный масштаб Core Loop | Что делает цикл |
|------|-------------------------------|-----------------|
| Шутер | 10-30 секунд | Боевой encounter |
| RPG | 2-5 минут | Бой → лут → прокачка |
| Стратегия | 5-15 минут | Ход → решение → результат |
| MMO-рейд | 15-30 минут | Попытка → анализ → коррекция |
| Настольная игра | 5-15 минут | Ход → взаимодействие → результат |
| Idle-игра | 30-60 секунд | Нажатие → награда → улучшение |

AI-система Gidede должна определять оптимальный масштаб Core Loop на основе жанра и целевой эстетики: Вызов требует коротких циклов (быстрая обратная связь), Открытие — средних (время на исследование), Подчинение — длинных (рутина с регулярным подкреплением).

## 4.9. Game Loop D&D: эталон формализованного цикла

D&D (Кн. 16) описывает свой игровой цикл как четырёхшаговый ритм:

1. **Мастер описывает сцену** — окружение, NPC, ситуацию
2. **Игроки описывают действия** — что их персонажи делают
3. **Мастер описывает результаты** — через правила (броски d20) или нарратив
4. **Возврат к шагу 1** — новая ситуация на основе результатов

### 4.9.1. Экономия действий как архитектура цикла

D&D формализует ограничения через **экономию действий**: 1 Action + 1 Bonus Action + 1 Reaction + Movement за ход. Это жёсткий бюджет, который заставляет игрока выбирать: что из доступного я сделаю этим ходом? Принцип: **ограниченные действия = осмысленный выбор**. Если игрок может сделать всё — нет выбора, нет стратегии, нет веселья.

Это переносимый дизайнерский паттерн: любой Core Loop можно проанализировать через его «бюджет действий». Что игрок может сделать за один цикл? Слишком много — перегрузка, нет фокуса. Слишком мало — ограниченность, скука. Оптимально — 3-5 значимых вариантов, из которых можно выбрать 1-2.

### 4.9.2. Четыре этапа прогрессии D&D

D&D разделяет прогрессию на четыре макро-цикла, каждый с собственным масштабом конфликтов:

| Этап | Уровни | Масштаб конфликтов |
|------|--------|-------------------|
| 1-й | 1-4 | Локальные угрозы; начинающие авантюристы |
| 2-й | 5-10 | Региональные угрозы; опытные герои |
| 3-й | 11-16 | Мировой масштаб; магия, меняющая реальность |
| 4-й | 17-20 | Мультивселенский масштаб; эпические архетипы |

Каждый этап — макро-цикл с собственной драматической аркой и масштабом последствий. Это модель *масштабирования Core Loop*: базовая структура цикла сохраняется, но масштаб растёт — от «спасти деревню» до «спасти мультивселенную». AI-система может использовать эту модель для генерации долгосрочной прогрессии: Core Loop остаётся неизменным, но контекст и ставки эскалируют.

## 4.10. Патологии Core Loop: диагностика и лечение

Объединяя диагностику из всех источников, мы можем выделить семь патологий Core Loop — типичных отказов, которые приводят к тому, что цикл «не работает»:

### 4.10.1. Runaway (Саморазгон)

**Симптом**: Игрок, получивший раннее преимущество, экспоненциально отрывается от остальных (PvP) или от сложности (PvE).

**Причина**: Усиливающая петля без балансирующей. Каждый проход через Core Loop увеличивает ресурсы, которые делают следующий проход легче, что увеличивает ресурсы ещё быстрее.

**Лечение**: Добавить тормозящий двигатель (налог, износ, расход), усиливающую сложность (враги растут быстрее, чем игрок), или отрицательную обратную связь (резиновая лента — отстающим легче).

### 4.10.2. Deadlock (Тупик)

**Симптом**: Игрок не может начать Core Loop, потому что ресурс, нужный для входа, производится только внутри цикла.

**Причина**: Круговая зависимость: для боя нужно снаряжение → для снаряжения нужны деньги → для денег нужно продать лут → для лута нужно победить врага → для победы нужно снаряжение.

**Лечение**: Обеспечить «затравочный» ресурс — начальное снаряжение, стартовый капитал, первый квест с гарантированной наградой. В AI-системе: проверять, что у каждого ресурса есть как минимум один источник, не зависящий от самого цикла.

### 4.10.3. Stall (Остановка)

**Симптом**: Core Loop замедляется до остановки — ресурсов недостаточно для продолжения.

**Причина**: Потребление превышает производство в устойчивом состоянии. Или: стоимость входа в цикл растёт быстрее, чем способность игрока платить.

**Лечение**: Увеличить производство, уменьшить потребление, или добавить альтернативные источники ресурсов. В AI-системе: моделировать потоки ресурсов через Machinations и проверять, что производство ≥ потребление при любом устойчивом состоянии.

### 4.10.4. Grind (Гринд)

**Симптом**: Каждый проход через Core Loop идентичен предыдущему — нет вариации, нет новых решений, нет роста.

**Причина**: Прибыльный конверсионный цикл без динамической настройки. Ресурсы растут, но геймплей не меняется.

**Лечение**: Ввести динамическую настройку прибыльности (цикл переходит от прибыльного к убыточному), добавить новые механики на определённых этапах прогрессии, ввести эмерджентные элементы (рандомизация, адаптивный AI врагов). В AI-системе: генерировать «кривую инновации» — график, показывающий, когда в Core Loop добавляются новые элементы.

### 4.10.5. Frustration Plateau (Фрустрационное плато)

**Симптом**: Игрок застревает на одном уровне сложности, не прогрессируя и не регрессируя.

**Причина**: Убыточный конверсионный цикл без «прорыва». Ресурсы убывают, но нет альтернативного пути к прогрессии.

**Лечение**: Добавить альтернативные стратегии (другой путь через Core Loop), снизить сложность для конкретного этапа (динамическая настройка сложности), или предоставить «аварийный» ресурс (компенсация за повторные неудачи — как в Celeste, где после нескольких смертей появляются дополнительные платформы).

### 4.10.6. Disconnected Loops (Разрыв петель)

**Симптом**: Микро-циклы не связаны с макро-циклами. Бой приносит удовольствие, но не влияет на прогрессию; прокачка влияет на прогрессию, но не на бой.

**Причина**: Отсутствие конверсионных цепей между уровнями. Результаты микро-цикла не «поднимаются» к макро-циклу.

**Лечение**: Проектировать Core Loop снизу вверх, обеспечивая, что каждый уровень вкладывается в следующий. Использовать метод концентрических диаграмм Зубека для визуализации связей. В AI-системе: проверять, что каждый ресурс, производимый на микро-уровне, потребляется на мезо- или макро-уровне.

### 4.10.7. Loop Overload (Перегрузка цикла)

**Симптом**: Слишком много решений за один проход Core Loop — когнитивная перегрузка, паралич выбора.

**Причина**: Нарушение интерактивного бюджета. Слишком много типов ресурсов, слишком много вариантов действий, слишком много информации для отслеживания.

**Лечение**: Упростить Core Loop до 3-5 ключевых решений за цикл. Использовать принцип «фиксированных действий» (как экономия действий в D&D). Скрыть сложность: базовый Core Loop прост, продвинутые опции открываются постепенно. В AI-системе: генерировать Core Loop с контролируемым фактором ветвления.

## 4.11. Конструирование Core Loop: метод для Gidede

Объединяя все модели, мы формулируем пошаговый метод конструирования Core Loop для AI-системы Gidede:

### 4.11.1. Шаг 1: Определить целевую эстетику и жанр

Вход: целевая эстетика (из Reverse MDA) + жанр + целевая аудитория.

Выход: профиль Core Loop — доминирующий тип эстетики определяет тип Core Loop:
- Вызов → Engine (нарастающая сложность)
- Открытие → Economy (новые ресурсы и цепочки)
- Товарищество → Ecology (социальный баланс)
- Подчинение → Engine (ритуальный цикл)

### 4.11.2. Шаг 2: Сформулировать Core Loop в одном предложении

Пройти пять вопросов Гэри: Какой цикл? В чём конфликт? Какие ресурсы? Какое взаимодействие? В чём цель? Если Core Loop не описывается в одном предложении — упростить.

### 4.11.3. Шаг 3: Определить масштаб Core Loop

На основе жанра определить оптимальную длительность одного прохода (от 10 секунд для шутера до 15 минут для стратегии). Это определяет «частоту пульса» игры.

### 4.11.4. Шаг 4: Спроектировать конверсионный цикл

Определить ресурсы и их конверсионные цепи (Зубек). Убедиться, что:
- Каждый ресурс имеет как минимум один источник и один сток
- Цикл не является чисто прибыльным (риск гринда) или чисто убыточным (риск фрустрации)
- Динамическая настройка прибыльности обеспечена

### 4.11.5. Шаг 5: Построить вложенные петли

Используя концентрические диаграммы Зубека, спроектировать микро → малый → средний → крупный → макро циклы. Убедиться, что:
- Каждый уровень вложен в следующий (результаты микро-цикла питают мезо-цикл)
- Нет разрывов между уровнями
- Обратная связь присутствует на каждом уровне

### 4.11.6. Шаг 6: Проверить на патологии

Пройти чек-лист семи патологий: Runaway? Deadlock? Stall? Grind? Frustration Plateau? Disconnected Loops? Loop Overload? При обнаружении патологии — применить соответствующее лечение.

### 4.11.7. Шаг 7: Прототип и валидация

«Закрыть петлю» (Селлерс): обеспечить, что игрок может действовать, видеть результат и учиться. Если базовая петля не приносит удовольствия — не строить поверх неё. Итерировать: цикл дизайнера (Селлерс) → цикл модели игры → цикл ментальной модели игрока → интерактивная петля → уточнение.

| **Among Us** | Выполнять задачи → наблюдать за другими → подозревать → голосовать → исключать | Ecology + Social | Задачи, подозрения, алиби | Кто эмитент? Доверять или нет? |

## 4.13. Итоги: Core Loop как ядро генерации

Core Loop — не один из многих элементов игры; это *фундамент*, на котором строится всё остальное. Без работающего Core Loop не работают ни прогрессия, ни баланс, ни нарратив — потому что всё это существует *внутри* Core Loop, обогащая и направляя его.

Для AI-системы Gidede Core Loop — **первый артефакт генерации**: прежде чем генерировать механики, экономику, прогрессию или нарратив, AI должен сгенерировать Core Loop. И прежде чем добавлять сложность — убедиться, что базовая петля замкнута и приносит удовольствие.

Модели, рассмотренные в этой главе, дают AI полный инструментарий для конструирования Core Loop:
- **Петля взаимодействия Кука** — для моделирования когнитивного цикла
- **Концентрические циклы Зубека** — для проектирования вложенных петель
- **Типология Селлерса** — для определения структурного типа (Engine/Economy/Ecology)
- **Цикл прогрессии Шрайбера** — для управления темпом и мотивацией
- **Конверсионные цепи Зубека** — для проектирования экономики цикла
- **Пять вопросов Гэри** — для верификации чёткости замысла
- **«30 секунд веселья»** — для определения оптимального масштаба
- **Диагностика патологий** — для выявления и лечения типичных отказов
