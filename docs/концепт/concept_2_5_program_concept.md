## 2.5.1 Целевая аудитория и сценарии использования

### Целевая аудитория

Gidede — это AI-first инструмент для геймдизайна, который адресует три ключевые проблемы индустрии: высокую стоимость качественного геймдизайна, отсутствие формализованных методологий в большинстве студий, и пропасть между теорией (книги) и практикой (реальные проекты). Система объединяет формальные фреймворки из 17 книг по геймдизайну с генеративными возможностями AI, создавая интеллектуального ассистента, который не заменяет дизайнера, а усиливает его.

#### Сегмент 1: Инди-разработчики-одиночки (Primary)

Инди-разработчик, работающий в одиночку или с командой до 3 человек, — это пользователь, который одновременно выполняет роли продюсера, геймдизайнера, программиста и художника. У него нет бюджета на нанятого геймдизайнера, нет времени на глубокое изучение 17 книг по теории, но есть потребность в качественном геймдизайне. Этот сегмент составляет крупнейшую растущую группу в индустрии — по данным Steam, более 60% всех опубликованных игр создаются командами из 1-3 человек.

**Профиль пользователя**:
- Возраст: 22-38 лет
- Опыт: 1-5 лет в разработке игр
- Технический стек: Unity/Godot/Unreal, базовое программирование
- Боль: «Я умею программировать, но не знаю, как сделать игру весёлой»
- Мотивация: Создать игру, в которую люди действительно хотят играть
- Контекст использования: Вечерняя/выходная разработка, ограниченное время

**Ключевые потребности**: Быстрая генерация концепции игры из абстрактной идеи, проверка баланса без глубоких математических знаний, структурированная документация (GDD) для себя и для потенциальных издателей, навигация по фреймворкам геймдизайна без необходимости читать книги.

#### Сегмент 2: Начинающие геймдизайнеры (Secondary)

Студент профильного вуза или выпускник курсов по геймдизайну, который знает теорию на уровне определений, но не умеет применять её на практике. Этот пользователь знаком с терминами «MDA», «Core Loop», «flow», но не имеет опыта превращения этих концепций в рабочие механики. Для него Gidede становится «учителем практики», который показывает, как абстрактные фреймворки работают в реальных проектах.

**Профиль пользователя**:
- Возраст: 19-26 лет
- Опыт: Обучение или первые стажировки
- Технический стек: Базовый, изучает инструменты
- Боль: «Я знаю теорию, но не могу превратить её в конкретные механики»
- Мотивация: Приобрести практические навыки геймдизайна
- Контекст использования: Учебные проекты, портфолио, хакатоны

**Ключевые потребности**: Интерактивное изучение фреймворков (не текст, а действие), примеры применения каждого концепта к реальным играм, пошаговые инструкции «от идеи до механики», валидация собственных решений через формальные чек-листы.

#### Сегмент 3: Продюсеры и лиды малых студий (Tertiary)

Продюсер или lead game designer студии из 10-30 человек, которому нужен инструмент для стандартизации процесса геймдизайна в команде. Этот пользователь уже имеет опыт, но нуждается в системе, которая обеспечит качество и консистентность решений геймдизайна на протяжении проекта, а также поможет онбордингу новых членов команды.

**Профиль пользователя**:
- Возраст: 28-42 года
- Опыт: 5-15 лет в индустрии
- Технический стек: Полный, фокус на управлении
- Боль: «Каждый дизайнер работает по-своему, нет стандарта качества»
- Мотивация: Повысить качество и скорость принятия дизайнерских решений
- Контекст использования: Производственные встречи, ревью дизайна

**Ключевые потребности**: Стандартизированные чек-листы для ревью, формализованный процесс от концепции до GDD, аналитика баланса и экономики для принятия решений на основе данных, интеграция с существующим производственным пайплайном.

### Сценарии использования

#### Сценарий 1: «От идеи до концепции» (Indie Dev)

Алексей — инди-разработчик, у которого есть смутная идея: «Хочу сделать roguelike про алхимика, который варит зелья и сражается с монстрами». Он вводит эту идею в Gidede. Система определяет жанр (roguelike), целевую эстетику (Вызов + Открытие — из модели ЛеБланка), предлагает Core Loop (Собрать ингредиенты → Варить зелье → Испытать в бою → Получить новый рецепт → Улучшить лабораторию), подбирает совместимые механики из MechanicsDB (Crafting + Procedural Generation + permadeath + Resource Management), и генерирует One-Pager с USP: «Единственный roguelike, где крафт — это бой, а бой — это крафт». Алексей итерирует: меняет эстетику на «Фантазия + Вызов», и система перестраивает рекомендации, предлагая более нарративно-ориентированные механики. За 30 минут вместо недель брейншторма у него есть конкретная, валидированная концепция.

#### Сценарий 2: «Проверка баланса» (Junior Designer)

Мария — junior game designer, работающая над системой боя для мобильной RPG. Она создала 8 классов персонажей с характеристиками, но не уверена, сбалансированы ли они. Она загружает данные в Gidede, и система: (1) классифицирует боевую систему как Ecology (балансирующие петли с конвертацией ресурсов — Кн. 13), (2) запускает transitive-анализ (сравнение cost-power кривых каждого класса — Кн. 7), (3) обнаруживает, что класс «Берсерк» имеет некомпенсированную усиливающую петлю (больше урон → больше здоровья → ещё больше урон), (4) предлагает три варианта коррекции: добавить тормозящий двигатель (усталость после ярости), снизить множитель, ввести ситуационную зависимость. Мария выбирает вариант 1, система обновляет модель и показывает симуляцию: до коррекции — runaway после 5-го уровня, после — стабильное равновесие.

#### Сценарий 3: «Генерация GDD» (Small Studio Lead)

Дмитрий — lead designer, которому нужно подготовить GDD для издателя к концу недели. Его команда из 12 человек работала над прототипом 2 месяца, и у них есть разрозненные документы: таблицы баланса в Google Sheets, нарративный бриф в Notion, концепт-арты в Miro. Он загружает ключевые данные в Gidede, и система: (1) генерирует структуру GDD по шаблону из 38 секций (Кн. 8), адаптированному под жанр (action-RPG), (2) заполняет разделы Mechanics и Balance на основе загруженных таблиц, (3) генерирует раздел Narrative на основе брифа, дополняя его матрицей квестов (8 типов x 4 паттерна), (4) создаёт Machinations-диаграмму экономики, (5) добавляет чек-лист из 113 линз Шелла с автоматической оценкой по релевантным линзам. Дмитрий редактирует, дополняет и экспортирует финальный PDF — за 2 дня вместо недели.

#### Сценарий 4: «Обучение через практику» (Student)

Олег — студент, изучающий геймдизайн. Он хочет понять, как MDA-фреймворк работает на практике. В Gidede он открывает интерактивный модуль «MDA Lab»: вводит механики своей учебной игры (платформер с двойным прыжком и стенобегом), система анализирует их через классический MDA (Mechanics → Dynamics → Aesthetics) и показывает: какие динамики возникают (время как ресурс, точность как навык), какие эстетические ценности поддерживаются (Вызов, Чувственное удовольствие), а какие — нет. Затем Олег переключается в Reverse MDA-режим: выбирает эстетику «Открытие + Вызов», и система предлагает дополнительные механики (скрытые области, procedural generation уровней), генерируя из MechanicsDB с учётом совместимости. Олег видит полный цикл MDA «в обе стороны» и понимает, как дизайнер может двигаться от желаемого опыта к конкретным правилам.

#### Сценарий 5: «Интеграция с GDCombine» (Studio Workflow)

Команда использует GDCombine (GBE) как основное средство документации. Продюсер хочет добавить AI-анализ к существующему проекту. Через плагин Gidede для GBE она: (1) запускает MDA-анализ текущего проекта — Gidede читает Blueprint-данные через API GBE, (2) получает отчёт о соответствии механик заявленной эстетике, (3) обнаруживает лудонарративный диссонанс (нарратив: «мир на грани гибели», механики: спокойный фарминг без давления), (4) принимает рекомендации, корректирует Blueprint в GBE, (5) генерирует обновлённый GDD через шаблоны GBE с учётом новых данных от Gidede. Рабочий процесс не прерывается — AI-анализ встроен в существующий пайплайн.

## 2.5.2 Функциональные блоки программы

### Обзор архитектуры функциональных блоков

Блоки спроектированы как самостоятельные модули, которые могут работать независимо, но обмениваются данными через единую модель проекта. Архитектура следует принципу «от опыта к механике» — Reverse MDA как центральный генеративный принцип, с валидацией через классический MDA и формальные чек-листы.

### Блок 1: Генератор концепции (Concept Generator)

Генератор концепции — точка входа в Gidede, которая превращает абстрактную идею в структурированную концепцию игры. Блок реализует пайплайн из 5 шагов, основанный на Reverse MDA (Бонд, Кн. 17) и алгоритме генерации из Кн. 15 (SW.BAND).

**Входные данные**:
- Жанр (выбор из 20+ жанров или свободный ввод)
- Целевая аудитория (модель Йи: 12 типов в 3 кластерах)
- Ограничения (платформа, бюджет, размер команды)
- Текстовое описание идеи (1-3 предложения)
- Референтные игры (опционально)

**Процесс**:
1. **Анализ входа**: Определение жанра, маппинг на эстетику ЛеБланка через модель Йи (какие мотивации доминируют у выбранной ЦА)
2. **Reverse MDA — Эстетика**: Выбор 2-3 доминантных эстетических ценностей (из 8 типов ЛеБланка), которые должны возникнуть у игрока
3. **Reverse MDA — Динамика**: Вывод динамик, которые порождают выбранную эстетику (используя таблицу соответствий из Библии геймдизайна, раздел 2.3)
4. **MechanicsDB — Механики**: Выбор совместимых механик из 127 карт (Кн. 15) с учётом модели совместимости (синергии/конфликты/нейтральность) и матрицы «Механика → Жанр»
5. **Валидация**: Проверка через Triangle of Weirdness (Кн. 8), 8 фильтров идеи (Кн. 1), 5 вопросов кор-геймплея (Кн. 10)

**Выходные данные**:
- One-Pager: Название, жанр, ЦА, USP, 3 уникальные фичи, референты
- Эстетический профиль: доминантные эстетики с обоснованием
- Набор рекомендуемых механик с оценкой совместимости
- Предварительный Core Loop (переход к Блоку 2)

**Ключевые алгоритмы**:
- `mapAudienceToAesthetics()`: Модель Йи (12 типов) → Эстетика ЛеБланка (8 типов)
- `selectMechanics()`: 7-шаговый алгоритм из Кн. 15 — выбор + фильтрация + ранжирование
- `validateConcept()`: Triangle of Weirdness + фильтры Шелла + вопросы Гэри
- `generateUSP()`: AI-генерация уникального торгового предложения на основе выбранных механик

### Блок 2: Core Loop Designer

Конструктор Core Loop — визуальный инструмент для проектирования основного цикла игры. Блок реализует 4-уровневую модель петель (Кн. 6: микро → малый → средний → крупный → макро) с визуализацией и анализом.

**Входные данные**:
- Концепция из Блока 1 или ручной ввод
- Тип Core Loop (5 типов из GDCombine + 3 структурных типа Селлерса: Engine/Economy/Ecology)

**Процесс**:
1. **Определение структурного типа**: Классификация Core Loop как Engine (усиливающие петли, один ресурс), Economy (усиливающие + конвертация), или Ecology (балансирующие + конвертация)
2. **Конструирование петель**: Визуальный редактор для создания цепочки навыков (микро → мезо → макро → мета-петли)
3. **Диагностика**: Проверка на 7 патологий (runaway, deadlock, stall, и др. — Кн. 13)
4. **Валидация**: Тест «30 секунд веселья» (Кн. 7) — формализованный чек-лист

**Выходные данные**:
- Визуальная диаграмма Core Loop (интерактивная, с анимацией потока ресурсов)
- Структурный тип с обоснованием
- Диагноз патологий (если есть)
- Связь с MechanicsDB (какие механики реализуют каждую петлю)

**Ключевые алгоритмы**:
- `classifyCoreLoop()`: Определение типа по двум осям (петля × ресурсная конвертация)
- `diagnosePathologies()`: Проверка на runaway, deadlock, stall, brittleness
- `buildSkillChain()`: Автоматическое построение цепочки навыков из механик
- `validateFunCheck()`: Формализованный чек-лист «30 секунд веселья»

### Блок 3: Механики и MDA Lab

MDA Lab — интерактивная среда для работы с двойным MDA-процессом (генеративный + аналитический). Это самый интеллектуально насыщенный блок, объединяющий MechanicsDB, 113 линз Шелла и матрицу 4×3 Бонда.

**Режим 1: Генеративный (Reverse MDA)**
- Вход: Желаемая эстетика (2-3 из 8 типов)
- Процесс: Эстетика → Динамики → Механики из MechanicsDB
- Выход: Набор рекомендованных механик с оценкой совместимости

**Режим 2: Аналитический (Classic MDA)**
- Вход: Существующие механики (ручной ввод или из проекта)
- Процесс: Механики → Динамики → Эстетика (что ощущает игрок?)
- Выход: Карта эстетических ценностей, выявленные разрывы

**Режим 3: Валидационный (Линзы Шелла)**
- Вход: Проект целиком (механики + нарратив + опыт)
- Процесс: Последовательный опрос по релевантным линзам из 113
- Выход: Отчёт с оценками по каждой релевантной линзе, приоритизированный список проблем

**Режим 4: Аналитический (Матрица 4×3 Бонда)**
- Вход: Проект целиком
- Процесс: Анализ по 4 элементам × 3 уровням (Фиксированный/Динамический/Культурный)
- Выход: Матрица с заполненными ячейками, выявленные дисбалансы

**Ключевые алгоритмы**:
- `reverseMDA()`: Aesthetics → Dynamics → Mechanics (используя таблицу соответствий + AI)
- `classicMDA()`: Mechanics → Dynamics → Aesthetics (симуляция взаимодействия)
- `lensAudit()`: Выбор релевантных линз + генерация вопросов + оценка ответов
- `bondMatrixAnalysis()`: Заполнение матрицы 4×3 + выявление дисбалансов
- `checkLudonarrative()`: Обнаружение лудонарративного диссонанса (Гармония/Ирония/Диссонанс)

### Блок 4: Баланс и симуляция

Модуль балансировки — формальный аппарат для математического анализа и коррекции баланса игры. Объединяет 7 типов баланса (Кн. 7), 12 типов баланса (Библия 2.5) и симуляционные инструменты.

**Подблок 4.1: Анализ баланса**
- Transitive-анализ: Cost-power кривые, формулы стоимости (Кн. 7)
- Intransitive-анализ: Rock-Paper-Scissors матрицы, доминантные стратегии (Кн. 7)
- Ситуационный баланс: Контекстная ценность, региональная оценка (Кн. 7)
- Q-фактор: Выявление избыточных компонентов (Кн. 12)

**Подблок 4.2: Симуляция**
- Monte Carlo: Моделирование тысяч боёв/сессий для проверки баланса
- Machinations-симуляция: Визуальная симуляция экономики игры (Кн. 4)
- Анализ стабильности: Проверка петель обратной связи на 6 комбинаций (Кн. 7)

**Подблок 4.3: Прогрессия**
- Кривые прогрессии: 7 типов кривых с визуальным редактором (Кн. 7)
- Формулы роста: (Prev × Mult) + Add = New Step с рекомендациями (Кн. 9)
- Макро-модель: T часов → L уровней → контент-план (Кн. 7)

**Ключевые алгоритмы**:
- `transitiveBalance()`: Расчёт cost-power кривых, выявление пере-/недооценённых элементов
- `intransitiveBalance()`: Поиск доминантных стратегий через матричный анализ
- `monteCarloSimulate()`: N-прогонов боёв/экономики с агрегацией результатов
- `machinationsSimulate()`: Выполнение Machinations-модели с визуализацией
- `analyzeFeedbackStability()`: Определение типа петли (6 комбинаций) + прогноз поведения
- `generateProgressionCurve()`: Построение и оптимизация кривых прогрессии

### Блок 5: Экономика и прогрессия

Модуль экономического моделирования — конструктор внутренней экономики игры на основе Machinations (Кн. 4) и типологии Селлерса (Кн. 13). Позволяет проектировать, визуализировать и симулировать ресурсные потоки.

**Подблок 5.1: Конструктор экономики**
- Визуальный редактор Machinations-диаграмм: Pool, Source, Drain, Converter, Trader, Register, Gate, Activator, Trigger, Delay, Queue
- Типизация систем: Engine / Economy / Ecology (Кн. 13)
- Шаблоны: 16+ паттернов Adams & Dormans как стартовые точки
- Искусственные игроки: Автоматические стратегии для симуляции

**Подблок 5.2: Диагностика экономики**
- Runaway detection: Выявление некомпенсированных усиливающих петель
- Deadlock/stall detection: Обнаружение блокировок ресурсных циклов
- Инфляция/стагнация/арбитраж: 3 патологии (Кн. 13)
- Faucet/drain баланс: Проверка равновесия источников и стоков

**Подблок 5.3: Прогрессия и контент-план**
- Кривые прогрессии: Выбор и настройка из 7 типов
- Макро-модель RPG: Расчёт контент-плана (уровни, враги, способности)
- Двигатели прогрессии: XP → уровни → способности → контент
- Эмерджентная прогрессия: Фазы экономики (начальная → рост → зрелость → завершение)

**Ключевые алгоритмы**:
- `buildMachinationsModel()`: Конвертация пользовательского ввода в Machinations-граф
- `classifyEconomicSystem()`: Engine/Economy/Ecology по двум осям
- `diagnoseEconomy()`: Runaway + deadlock + stall + патологии
- `balanceFaucetsDrains()`: Автоматическая коррекция источников и стоков
- `planContentCurve()`: Генерация контент-плана из макро-модели

### Блок 6: GDD Generator и чек-листы

Генератор дизайн-документов и система валидационных чек-листов. Объединяет шаблоны из 5 источников (Шелл, Роджерс, Андрианова/Яковлева, Роллингс/Моррис, Селлерс) с AI-генерацией содержимого.

**Подблок 6.1: Шаблоны GDD**
- One-Pager: 8 полей (Кн. 8) — для быстрой концепции
- 10-страничный GDD: Структура от Селлерса (Кн. 13) — для прототипа
- 38-секционный GDD: Полный шаблон Роджерса (Кн. 8) — для производства
- Нарративная документация: 11 типов (Кн. 3) — бриф, синопсис, сторилайн
- Art Bible: Шаблон визуального стиля
- Концепт-документ: 3 раздела от Селлерса — для издателя

**Подблок 6.2: AI-заполнение**
- Автоматическое заполнение секций GDD из данных проекта
- Генерация описаний механик, нарратива, визуала
- Контекстная подсказка: «Для этого раздела обычно описывают...»
- Цитирование источников: Ссылки на конкретные книги и концепции

**Подблок 6.3: Чек-листы валидации**
- 113 линз Шелла: Интерактивный опрос с оценкой
- MDA-чек: Проверка полноты (механики → динамики → эстетика)
- Баланс-чек: 12 типов баланса, автоматическая проверка
- Нарратив-чек: Лудонарративный диссонанс, агентивность, структура
- Экономика-чек: Runaway, deadlock, faucet/drain, патологии

**Ключевые алгоритмы**:
- `generateGDD()`: Выбор шаблона + заполнение из Project State + AI-генерация пробелов

- `exportDocument()`: Генерация PDF/DOCX из заполненного шаблона

### Блок 7: AI-ассистент

AI-ассистент — контекстно-осведомлённый чат-бот, который знает о проекте пользователя всё и может давать релевантные рекомендации в любом модуле. Это не отдельный модуль, а «слой интеллекта», пронизывающий все блоки.

**Возможности**:
- Контекст проекта: Ассистент знает текущее состояние проекта, выбранные механики, эстетику, баланс
- Фреймворк-осведомлённость: Ссылается на конкретные концепции из 17 книг (MDA, линзы, паттерны)
- Режимы работы: (1) Свободный чат — вопросы о геймдизайне, (2) Контекстные подсказки — рекомендации в конкретном модуле, (3) Гайдed tour — пошаговое прохождение процесса дизайна
- Проактивность: Если обнаруживает проблему (runaway, диссонанс), сам предлагает решение

**Контекстные подсказки по модулям**:
- В Блоке 1: «Для roguelike с эстетикой Вызов обычно рекомендуются механики permadeath + процедурная генерация. Добавить?»
- В Блоке 2: «Ваш Core Loop — Engine-тип без тормозящего двигателя. Это может привести к runaway. Рекомендую добавить drain-механику»
- В Блоке 3: «Линза #42 «Поток» показывает, что кривая сложности не соответствует кривой навыка. Нужно добавить промежуточные чекпойнты»
- В Блоке 4: «Берсерк имеет cost/power ratio 0.73 — значительно ниже среднего 1.0. Это дисбаланс»

**Архитектура AI-ассистента**:
- System Prompt = «Библия геймдизайна» (структурированные знания из Фазы 2) + контекст проекта
- RAG (Retrieval Augmented Generation): Векторная БД с фрагментами из 17 книг для цитирования
- Мульти-модальность: Текст + визуал (Machinations-диаграммы, графики баланса)
- Память сессии: Контекст разговора + история проекта

### Блок 8: Интеграция с GDCombine (опционально)

Модуль интеграции с GDCombine (GBE) реализует стратегию «Вариант A → Вариант D» из анализа интеграции. Позволяет Gidede работать как в режиме плагина для GBE, так и в режиме самостоятельного приложения с API-мостом.

**Режим плагина (Вариант A)**:
- BlueprintTypeProvider: Новые типы — MDAModel, LensChecklist, MachinationsDiagram, BalanceAnalysis
- LinterRuleProvider: Правила MDA-валидации, линзы Шелла, эмерджентность, диссонанс
- DocumentTemplateProvider: Шаблоны Библии геймдизайна, MDA-анализа, Machinations-отчёта
- PresetProvider: Жанровые пресеты на основе 17 книг

**Режим API-моста (Вариант D)**:
- Gidede → GBE: AI-генерированные Blueprint, результаты анализа
- GBE → Gidede: Структурированные данные проекта, документы, экспорт

**Ключевые алгоритмы**:
- `syncProjectToGBE()`: Экспорт Project State в формат Blueprint GBE
- `syncProjectFromGBE()`: Импорт Blueprint GBE в Project State Gidede
- `runLinterRules()`: Применение правил Gidede через LinterRuleProvider GBE

## 2.5.3 AI-интеграция: что генерирует ИИ, что — алгоритмы

### Принцип разделения ответственности

Ключевой архитектурный принцип Gidede — чёткое разделение между тем, что делает AI (генерация, интерпретация, креативные рекомендации), и тем, что делают детерминированные алгоритмы (расчёты, симуляция, валидация). Это обеспечивает надёжность (алгоритмы всегда дают одинаковый результат для одних и тех же данных), прозрачность (пользователь понимает, почему система рекомендует именно это), и экономичность (алгоритмы бесплатны, AI имеет стоимость за токен).

Разделение следует правилу: **Алгоритмы — для вопросов «сколько» и «правильно ли», AI — для вопросов «что если» и «почему»**. Алгоритмы дают точные ответы на формализованные вопросы; AI генерирует варианты, интерпретирует результаты и объясняет рекомендации на языке геймдизайна.

### Матрица распределения задач

| Функция | AI | Алгоритм | Обоснование |
|---------|-----|----------|-------------|
| Генерация концепции игры | ✅ Основной | ⬜ | Креативная задача, требует синтеза из разнородных данных |

### AI-промпт-архитектура

Каждый модуль Gidede использует специализированную промпт-стратегию. Промпты строятся из трёх слоёв:

**Слой 1: System Prompt (статичный)**
Базовая роль AI-ассистента Gidede, определённая на основе «Библии геймдизайна». Содержит: рабочее определение игры, пятислойную модель, основные фреймворки (MDA, MechanicsDB, типология Селлерса). Этот слой загружается один раз при инициализации сессии и остаётся неизменным.

**Слой 2: Context Prompt (динамический, из Project State)**
Текущее состояние проекта пользователя: выбранный жанр, эстетика, механики, Core Loop, данные баланса, нарратив. Этот слой обновляется при каждом изменении проекта и обеспечивает контекстную осведомлённость AI.

**Слой 3: Task Prompt (специфичный для модуля)**
Конкретная задача в конкретном модуле: «Сгенерируй 5 вариантов USP для RPG про алхимика» или «Объясни, почему класс Берсерк имеет runaway-эффект». Содержит формат ожидаемого ответа и ограничения.

**RAG-уровень (по запросу)**
Когда пользователю нужны цитаты из книг или детали конкретного фреймворка, система извлекает релевантные фрагменты из векторной БД (embeddings 17 книг + Библии геймдизайна) и добавляет их в контекст промпта. Это обеспечивает фактологическую точность и возможность сослаться на источник.

| Операция | Модель | Примерная стоимость | Частота |
|----------|--------|-------------------|---------|

| Линзы Шелла | GPT-3.5 / Claude Haiku | ~$0.01-0.03 | 5-20/сессия |

**Стратегия оптимизации**: Использовать лёгкие модели (Haiku/GPT-3.5) для рутинных операций (чек-листы, оценки) и мощные модели (Sonnet/GPT-4) для креативных задач (генерация концепции, Reverse MDA). Кэшировать ответы на повторяющиеся запросы.

### Модель данных: Project State

Project State — единая структура данных, описывающая проект игры. Все модули читают и пишут в Project State через API, обеспечивая консистентность.

```typescript
interface ProjectState {
  // Метаданные
  id: string;
  name: string;
  createdAt: Date;
  updatedAt: Date;
  version: number;

  // Блок 1: Концепция
  concept: {
    genre: Genre;
    targetAudience: AudienceProfile;     // Модель Йи
    platform: Platform[];
    constraints: ProjectConstraints;
    onePager: OnePager;
    usp: string;
    referenceGames: string[];
  };

  // Блок 2: Core Loop
  coreLoop: {
    structuralType: 'engine' | 'economy' | 'ecology';
    loops: GameLoop[];                   // микро → мезо → макро → мета
    pathologyReport: PathologyReport;
    funCheckResult: FunCheckResult;
  };

  // Блок 3: MDA
  mda: {
    aesthetics: AestheticProfile[];      // Из 8 типов ЛеБланка
    dynamics: DynamicsMap;
    mechanics: SelectedMechanic[];       // Из MechanicsDB
    lensAudit: LensAuditResult;
    bondMatrix: BondMatrixResult;
    ludonarrativeCheck: LudonarrativeResult;
  };

  // Блок 4: Баланс
  balance: {
    transitiveAnalysis: TransitiveResult;
    intransitiveAnalysis: IntransitiveResult;
    situationalAnalysis: SituationalResult;
    monteCarloResults: MonteCarloResult[];
    feedbackStability: FeedbackStabilityMap;
  };

  // Блок 5: Экономика
  economy: {
    machinationsModel: MachinationsGraph;
    systemType: 'engine' | 'economy' | 'ecology';
    diagnostics: EconomyDiagnostics;

  };
```

## 2.5.5 UX/UI концепция

### Дизайн-принципы

UX Gidede строится на пяти принципах, выведенных из анализа сценариев использования и целевой аудитории:

**Принцип 1: Progressive Disclosure**. Пользователь не должен видеть все 113 линз Шелла при первом визите. Интерфейс раскрывает сложность постепенно: от простого ввода идеи → к детальному MDA-анализу → к тонкой настройке баланса. Каждый уровень глубины опционален — инди-разработчик может остановиться на One-Pager, продюсер — дойти до Monte Carlo-симуляции.

**Принцип 2: Визуальное мышление**. Геймдизайн — визуальная дисциплина. Machinations-диаграммы, Core Loop-графы, cost-power кривые, кривые прогрессии — всё это должно быть интерактивным, визуальным и живым. Текст — дополнение к визуалу, не наоборот.

**Принцип 3: Контекстный AI**. AI-ассистент не отдельное окно чата — он встроен в каждый модуль. Контекстные подсказки появляются релевантно: обнаружен runaway — появляется рекомендация; линза не пройдена — предлагается помощь. Пользователь может игнорировать AI и работать вручную, но помощь всегда доступна.

**Принцип 4: Живой проект**. Проект — это не статичный документ, а живая модель. Изменил механику — Core Loop перестроился, баланс пересчитался, GDD обновился. Каждое изменение распространяется через Project State, и пользователь видит последствия своих решений в реальном времени.

**Принцип 5: От результата к процессу**. Пользователь начинает с желаемого результата (какой опыт должна давать игра) и движется к конкретным правилам. Это Reverse MDA как UX-принцип: сначала «что», потом «как».

**Режим «Продвинутый»** (для опытных дизайнеров): Полный доступ ко всем параметрам, ручное управление каждым алгоритмом, возможность переопределить AI-рекомендации. Видны: формулы баланса, параметры Monte Carlo, ручное редактирование Machinations-модели.

**Режим «Обучение»** (для студентов): Каждый инструмент сопровождается объяснением: зачем он нужен, на каком фреймворке основан, как интерпретировать результат. Всплывающие подсказки с цитатами из книг. Пошаговые туториалы для каждого модуля.

## 2.5.6 Выбор технологического стека

### Критерии выбора

Технологический стек Gidede выбирается на основе 6 критериев, ранжированных по приоритету:

1. **AI-first совместимость**: Стек должен оптимально поддерживать интеграцию с LLM-провайдерами (OpenAI, Anthropic, локальные модели), RAG-системами, и потоковую генерацию. AI — не фича, а ядро продукта.

2. **Скорость разработки MVP**: Время до первого работающего прототипа критично. Стек должен минимизировать бойлерплейт и максимизировать переиспользование готовых решений.

3. **Визуализация и интерактивность**: Machinations-диаграммы, cost-power кривые, Core Loop-графы, Monte Carlo-анимации — всё это требует мощной визуализации. Нужна библиотека с поддержкой интерактивных графов и научных графиков.

4. **Интеграция с GDCombine**: GBE использует Python/FastAPI + Vue.js. Стек Gidede должен обеспечить бесшовную интеграцию через API, а в идеале — общие типы данных и протоколы.

5. **Масштабируемость**: От единственного пользователя до потенциального SaaS с тысячами сессий. Горизонтальное масштабирование backend, кэширование, фоновые задачи.

6. **Экосистема и поддержка**: Активное сообщество, документация, готовые библиотеки. Минимум «экзотических» зависимостей.

### Рекомендуемый стек

#### Frontend: Next.js 14+ (App Router) + TypeScript

**Обоснование**: Next.js — оптимальный выбор для AI-first приложения по нескольким причинам. Во-первых, Server Components позволяют обрабатывать AI-запросы на сервере без раскрытия API-ключей. Во-вторых, Streaming API и Server-Sent Events нативно поддерживают потоковую генерацию LLM-ответов. В-третьих, App Router с React Server Actions упрощает мутации Project State. В-четвёртых, огромная экосистема компонентов (shadcn/ui, Radix) ускоряет разработку UI. Альтернатива (Vue.js) была бы логичнее для интеграции с GBE, но Next.js даёт существенное преимущество в AI-интеграции и скорости разработки.

**Ключевые библиотеки**:
- `shadcn/ui` — компонентная библиотека (кнопки, формы, диалоги, таблицы)
- `reactflow` — интерактивные графы для Core Loop и Machinations
- `recharts` / `d3.js` — научные графики (cost-power кривые, Monte Carlo распределения)
- `vercel/ai` (AI SDK) — потоковая интеграция с LLM-провайдерами
- `zustand` — клиентское состояние (UI state, Project State cache)
- `zod` — runtime-валидация типов (общая с backend через shared schemas)

#### Backend: Python/FastAPI

**Обоснование**: Python — единственный реальный выбор для backend Gidede по трём причинам. Первая: все ML/AI-библиотеки — в Python (langchain, llama-index, scikit-learn для Monte Carlo). Вторая: полная совместимость с GBE (тот же стек), что упрощает интеграцию и переиспользование кода. Третья: богатая экосистема научных библиотек (numpy, scipy для расчётов баланса, networkx для Machinations-графов). FastAPI обеспечивает высокую производительность (async), автодокументацию (OpenAPI), и типизацию (Pydantic).

**Ключевые библиотеки**:
- `fastapi` + `uvicorn` — async веб-фреймворк
- `pydantic` — валидация и сериализация данных (shared types с frontend через JSON Schema)
- `sqlalchemy` + `asyncpg` — ORM для PostgreSQL
- `langchain` + `langchain-core` — AI-оркестрация, RAG, цепочки промптов
- `numpy` + `scipy` — математика баланса, статистика Monte Carlo
- `networkx` — графовые алгоритмы для Machinations
- `redis` — кэширование, Event Bus, сессии
- `celery` + `redis` — фоновые задачи (долгие симуляции, генерация документов)
- `weaviate` / `pgvector` — векторная БД для RAG (embeddings 17 книг)

#### База данных: PostgreSQL + pgvector

**Обоснование**: PostgreSQL — зрелая, надёжная реляционная БД, которая покрывает все потребности Gidede. Project State хранится как JSONB (гибкость схемы + SQL-запросы). pgvector добавляет векторный поиск для RAG без отдельного сервиса. JSONB позволяет хранить сложную иерархическую структуру Project State, при этом оставляя возможность индексировать и запрашивать отдельные поля.

**Схема хранения**:
- `projects` — основная таблица (id, user_id, name, state JSONB, created_at, updated_at)
- `project_versions` — версионность (id, project_id, version, state JSONB, diff)
- `knowledge_chunks` — RAG-хранилище (id, source_book, chapter, content, embedding vector)
- `chat_messages` — история AI-ассистента (id, project_id, role, content, context)
- `exports` — история экспортов (id, project_id, format, url, created_at)

#### AI-провайдеры: Мультипровайдерная архитектура

**Обоснование**: Ни один AI-провайдер не оптимален для всех задач. Для генерации концепции нужен мощный модель (GPT-4/Claude Sonnet), для чек-листов — быстрая и дешёвая (Haiku/GPT-3.5), для embeddings — специализированная. Мультипровайдерная архитектура с fallback chain обеспечивает надёжность и оптимизацию стоимости.

**Конфигурация**:
- Генерация концепции / Reverse MDA: `claude-sonnet` → `gpt-4o` (fallback)
- Чек-листы / интерпретация: `claude-haiku` → `gpt-3.5-turbo` (fallback)
- Embeddings: `text-embedding-3-small` (OpenAI) → локальный `all-MiniLM-L6-v2`
- Потоковый чат: `claude-sonnet` → `gpt-4o` (с SSE streaming)

### Альтернативы (рассмотренные и отвергнутые)

| Альтернатива | Почему отвергнута |
|-------------|-------------------|
| Vue.js frontend | Хуже экосистема для AI-интеграции, нет аналога Vercel AI SDK |
| Node.js backend | Слабее научные библиотеки, хуже интеграция с Python ML |
| MongoDB | Нет pgvector (нужен отдельный сервис для RAG), слабее транзакции |
| LangChain + Next.js API routes | Недостаточная изоляция AI-логики, проблемы с долгими задачами |
| Монолит (Next.js fullstack) | Ограничения для симуляций и ML, сложнее масштабировать |

## 2.5.7 MVP vs Full Version

### Принцип разделения

MVP (Minimum Viable Product) — это минимальный набор функционала, который решает главную проблему целевой аудитории и позволяет получить обратную связь. Для Gidede MVP решает проблему инди-разработчика: «Как превратить абстрактную идею в структурированную концепцию игры с валидированными механиками и Core Loop?» Full Version добавляет продвинутый анализ, симуляции и интеграцию.

Критерий включения в MVP: **может ли пользователь за 30 минут пройти путь от идеи до One-Pager с Core Loop и базовым MDA-анализом?** Если да — это MVP. Всё остальное — Full Version.

### MVP (версия 1.0)

**Срок разработки**: 6-8 недель  
**Целевая аудитория**: Инди-разработчики (Сегмент 1)  
**Цель**: Валидация ценности продукта — решает ли AI-ассистент реальную проблему

## Приложение B: Глоссарий архитектуры

| Термин | Определение |
|--------|------------|
| **Project State** | Единая структура данных (JSONB), описывающая текущее состояние проекта игры. SSOT для всех модулей |
| **MechanicsDB** | Каталог из 127 дискретных механик (4 уровня иерархии) с матрицей совместимости и жанровой привязкой |
| **Reverse MDA** | Генеративный процесс: Эстетика → Динамика → Механика (от Бонда, Кн. 17) |
| **Classic MDA** | Аналитический процесс: Механика → Динамика → Эстетика (Hunicke, LeBlanc, Zubek) |
| **Event Bus** | Асинхронная шина сообщений (Redis Pub/Sub) для событийного взаимодействия модулей |
| **RAG** | Retrieval Augmented Generation — поиск релевантных фрагментов знаний (17 книг) и добавление в контекст AI-промпта |
| **Machinations** | Визуальный язык моделирования игровых механик (Кн. 4, Adams & Dormans) — граф с типизированными узлами |
| **GBE** | GDCombine / Game Blueprint Engine — SSOT генератор документации для геймдизайна |
| **Runaway** | Патология усиливающей петли: рост без компенсации → экспоненциальный дисбаланс |
| **Deadlock** | Патология ресурсного цикла: ресурс нужен для запуска собственного производства |
| **SSOT** | Single Source of Truth — единый источник истины |
