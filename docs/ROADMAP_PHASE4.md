## 1. Обзор Фазы 4

### 1.1 Цели

Фаза 4 переводит теоретический фундамент (Фазы 1–3) в работающий программный продукт. Основные цели:

1. **Реализовать 8 функциональных блоков** (Блоки 1–8 из Концепции программы 2.5.2) как полнофункциональные модули веб-приложения
2. **Построить инфраструктуру**: авторизация, база данных, API-слой, AI-интеграция, кэширование
3. **Обеспечить сквозной поток данных**: от ввода идеи пользователем до генерации GDD с экспортом
4. **Интегрировать AI-компоненты**: 31 промпт (алгоритм 3.9) с маршрутизацией, кэшированием и fallback
5. **Создать качество production-уровня**: тестирование, обработка ошибок, производительность, UX

### 1.2 Критерии успеха

| # | Критерий | Метрика успеха |
|---|----------|---------------|
| C1 | Полный пайплайн «идея → GDD» | Пользователь может пройти весь путь за ≤ 60 минут |
| C2 | Все 8 блоков функциональны | Каждый блок проходит сценарий приёмки |
| C3 | AI-интеграция стабильна | 95%+ успешных AI-вызовов, fallback срабатывает при ошибках |
| C4 | Производительность | Время ответа API ≤ 2 сек (без учёта AI-латентности), AI-операции ≤ 30 сек |
| C5 | Данные сохраняются | Project State переживёт перезапуск сервера, нет потери данных |

| C7 | AI-ассистент контекстен | Ответы учитывают текущее состояние проекта |
| C8 | Код покрыт тестами | ≥ 60% coverage для backend, ≥ 50% для frontend |

## 5. Реестр рисков

### Риск 1: Нестабильность AI-ответов

**Описание**: AI-модели (OpenAI/Anthropic) могут возвращать невалидный JSON, галлюцинировать, менять формат ответа без уведомления. Это критично для 31 промпта, от которых зависит весь функционал.  
**Вероятность**: Высокая (уже наблюдается на практике)  
**Влияние**: Критическое — без AI не работает ни один блок  
**Митигация**:
- (1) Трёхуровневая валидация: синтаксическая → схемная → семантическая (реализовано в 3.9.5)
- (2) Fallback-цепочка: primary → fallback → cached → degraded
- (3) Детерминированные заглушки для 6 критичных промптов (3.9.5, таблица заглушек)
- (4) Регулярный мониторинг качества AI-ответов (автоматизированный eval)
- (5) Версионирование промптов — возможность отката на предыдущую версию

---

### Риск 2: Зависимость от внешних AI-провайдеров

**Описание**: Система полностью зависит от доступности OpenAI и Anthropic API. Rate limits, отключения, изменения цен — всё это влияет на работоспособность.  
**Вероятность**: Средняя  
**Влияние**: Высокое — недоступность AI = неработающая система  
**Митигация**:
- (1) Двухпровайдерная архитектура: OpenAI как primary, Anthropic как fallback (и наоборот)
- (2) Агрессивное кэширование: одинаковый запрос → cached ответ (Redis с TTL)
- (3) Self-hosted модель как последний fallback (Llama 3 / Mistral через vLLM для простых задач)
- (4) Graceful degradation: при недоступности AI система показывает детерминированные результаты (заглушки) с предупреждением
- (5) Мониторинг: алерт при error rate > 5%

---

### Риск 3: Сложность Machinations-симуляции

**Описание**: Реализация полноценного Machinations-движка (графовое выполнение с ресурсными потоками, условиями, обратными связями) — задача сложности XL, требующая значительных усилий и легко содержащая баги.  
**Вероятность**: Высокая  
**Влияние**: Среднее — Блок 5 не работает без Machinations, но остальные блоки функциональны  
**Митигация**:
- (1) MVP Machinations: поддержать только 5 базовых узлов (Source, Drain, Pool, Converter, Gate) без сложных условий
- (2) Итеративная реализация: сначала — выполнение модели без визуализации, потом — визуализация
- (3) Тестирование на 16 паттернах Adams/Dormans — каждый паттерн как тест-кейс
- (4) Рассмотреть использование open-source Machinations-библиотек (если существуют)
- (5) При невозможности полной реализации — заменить на упрощённую симуляцию (ресурсные таблицы вместо графа)

---

### Риск 4: Расползание скоупа (Scope Creep)

**Описание**: Каждый из 8 блоков может бесконечно дорабатываться. Линзы Шелла — 113 штук, каждый из которых требует отдельного промпта. MechanicsDB — 127 механик с матрицей совместимости. GDD — 38 секций. Соблазн «доделать всё» ведёт к затягиванию сроков.  
**Вероятность**: Высокая  
**Влияние**: Высокое — срыв сроков, незавершённый продукт  
**Митигация**:
- (1) Чёткий MVP для каждого блока: Блок 1 — 1 полный пайплайн, Блок 3 — 2 режима (Reverse + Classic), Блок 6 — 2 формата (one_sheet + full_gdd)
- (2) Приоритизация внутри блоков: сначала — auto_fill секции GDD, потом — ai_generate, потом — manual
- (3) Timeboxing: каждая субфаза имеет жёсткий дедлайн; если задача не готова — урезаем скоуп
- (4) Практика «80/20»: 80% ценности доставляют 20% функционала (Reverse MDA > Classic MDA > Линзы > Матрица Бонда)
- (5) Отдельный бэклог «v2.0» для фич, не вошедших в первый релиз

---

### Риск 5: Проблемы с производительностью AI-вызовов

**Описание**: Полный пайплайн «идея → GDD» может требовать 20–30 AI-вызовов. При средней латентности 3–5 сек на вызов — суммарное время 60–150 сек. Пользователь не будет ждать 2+ минуты.  
**Вероятность**: Средняя  
**Влияние**: Высокое — плохой UX, отказ от использования  
**Митигация**:
- (1) Параллельные AI-вызовы: независимые промпты выполняются одновременно (asyncio.gather)
- (2) Потоковый UI: показывать результаты по мере поступления (SSE), а не ждать все
- (3) Прогрессивная генерация: каждый блок работает независимо, не нужно ждать весь пайплайн
- (4) Кэширование промежуточных результатов: если пользователь изменил только эстетику — пересчитать только зависящие промпты
- (5) Фоновая обработка: длительные операции (Monte Carlo, Machinations) выполнять в Celery worker-ах с уведомлением по завершении
