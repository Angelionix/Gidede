# Gidede — Руководство пользователя

## Введение

**Gidede** — интеллектуальная система для геймдизайна, которая помогает превратить абстрактную идею игры в полноценный проектный документ. Система основана на формализованных фреймворках из 17 книг по геймдизайну и использует AI для генерации, анализа и валидации проектных решений.

Gidede состоит из 8 функциональных блоков, каждый из которых решает конкретную задачу геймдизайна — от генерации концепции до создания дизайн-документа и интеграции с внешними инструментами. Данные между блоками передаются автоматически: результат одного блока становится входом для следующего, формируя сквозной пайплайн проектирования.

### Ключевые принципы

- **Reverse MDA** — система начинает с целевого опыта игрока (эстетика) и выводит из него механики, а не наоборот
- **Валидация на каждом этапе** — каждое проектное решение проверяется формальными критериями
- **AI как советник** — система предлагает варианты и выявляет проблемы, но окончательные решения принимает дизайнер
- **Единый источник истины** — все данные хранятся в Project State и автоматически синхронизируются между блоками

## Блок 1: Генератор концепции (/blocks/1)

### Назначение

Блок 1 — точка входа в систему Gidede. Он преобразует вашу абстрактную идею игры в структурированную концепцию, включая жанр, эстетический профиль, набор совместимых механик, варианты Core Loop и уникальные торговые предложения (USP). Алгоритм реализует **Reverse MDA** — подход, при котором проектирование идёт от целевого опыта (эстетики) к конкретным правилам (механикам), а не наоборот.

### Как использовать

1. **Введите идею** — опишите вашу задумку в 1–5 предложениях. Чем конкретнее описание, тем точнее результат
2. **Выберите жанр** — укажите жанр вручную или включите режим автоопределения (система проанализирует текст идеи и предложит 3 варианта с оценкой уверенности)
3. **Укажите целевую аудиторию** — выберите мотивации по модели Йи (1–3 из 12: Destruction, Excitement, Competition, Community, Challenge, Strategy, Completion, Power, Fantasy, Story, Design, Discovery) и уровень опыта (casual / midcore / hardcore)
4. **Укажите платформы** — PC, консоли, мобильные и т.д.
5. **Добавьте референтные игры** — перечислите через запятую игры, похожие на вашу задумку
6. **Укажите бюджет/команду** — solo, small, medium, large
7. **Запретите нежелательные механики** — если точно знаете, чего не хотите

Нажмите **«Сгенерировать концепцию»** или **«Запустить пайплайн 1→2→3»** для последовательной обработки в трёх блоках.

### Что вы получаете

Результат генерации — **One-Pager**, структурированный документ концепции, содержащий:

- **Жанр и поджанр** — с обоснованием выбора
- **Эстетический профиль** — 3 доминантные эстетики ЛеБланка (например: Вызов, Фантазия, Открытие) с ранжировкой: первичная, поддерживающая, опциональная
- **Профиль динамик** — 5–10 динамических паттернов, которые должны возникнуть в игре для порождения целевой эстетики
- **Набор механик** — 10–18 механик из MechanicsDB (127 механик в 15 группах), сгруппированных по структурным ролям (базовые, боевые, прогрессии, пространственные, социальные)
- **3 кандидата Core Loop** — варианты основного игрового цикла с описанием шагов и проверкой «30 секунд веселья»
- **3 кандидата USP** — уникальные торговые предложения в формате «Единственный [жанр], где [уникальная комбинация]»
- **Отчёт валидации** — проверка через Triangle of Weirdness (Роджерс), 5 вопросов кор-геймплея (Гэри) и 8 фильтров идеи (Шелл)

### Алгоритм

Алгоритм 3.1 состоит из 7 этапов:

1. **Анализ и определение жанра** — классификация идеи по таксономии Роджерса
2. **Reverse MDA: определение эстетики** — маппинг целевой аудитории → эстетика через модель Йи
3. **Reverse MDA: вывод динамик** — определение динамических паттернов из эстетики
4. **Выбор механик из MechanicsDB** — 7-шаговый процесс подбора совместимых механик
5. **Генерация Core Loop и USP** — конструирование циклов и уникальных предложений
6. **Валидация концепции** — проверка через 3 формальных валидатора
7. **Сборка One-Pager** — итоговый структурированный документ

### Советы

- **Будьте конкретны** — «RPG про алхимика в средневековом городе» даст лучший результат, чем «игра про магию»
- **Используйте референтные игры** — это помогает AI понять контекст и выделить уникальность вашей идеи
- **Запрещайте механики осознанно** — если вы точно знаете, что в игре не будет PvP или микротранзакций, укажите это, чтобы избежать ненужных вариантов
- **Не бойтесь нестандартных комбинаций** — система предупредит о нетипичных сочетаниях, но не отклонит их

## Блок 2: Core Loop Designer (/blocks/2)

### Назначение

Блок 2 углубляется в структуру основного игрового цикла (Core Loop). В отличие от Блока 1, который генерирует предварительный Core Loop как часть концепции, этот блок строит детальную, диагностированную и валидированную модель иерархии петель — от микро-петель (миллисекунды) до мета-петель (недели). Core Loop — это не просто «цикл действий», а иерархическая система вложенных петель, работающая на нескольких временных масштабах.

### Как использовать

1. Данные из Блока 1 автоматически заполняют входные параметры (концепция, предварительный Core Loop, набор механик)
2. **Классифицируйте структурный тип** — система определяет тип Core Loop по двум осям: тип петель (усиливающие/балансирующие) и тип ресурсных взаимодействий (один ресурс/конвертация). Результат: Engine, Economy или Ecology
3. **Просмотрите иерархию петель** — от микро-петли (нажатие → анимация → эффект) до мета-петли (сезоны, обновления)
4. **Диагностируйте патологии** — система автоматически проверяет Core Loop на 7 типов патологий
5. **Просмотрите рекомендации** — AI предлагает коррекции для обнаруженных проблем

### Что вы получаете

**CoreLoopProfile** — полная модель основного игрового цикла:

- **Структурный тип** — Engine / Economy / Ecology / Hybrid с подтипом (например, braked_engine, multi_currency_economy)
- **Иерархия петель** — 6 уровней: микро (мс), малая (1–2 мин), средняя (5–10 мин), крупная (15–30 мин), макро (часы), мета (недели)
- **Отчёт о патологиях** — список обнаруженных проблем с серьёзностью (critical/warning/info)
- **Валидация** — формальная проверка на устойчивость и сбалансированность
- **Рекомендации** — конкретные предложения по улучшению с приоритизацией

### Семь патологий Core Loop

Патология — это структурная проблема Core Loop, которая приводит к нежелательному игровому опыту:

| Патология | Описание | Признаки |
|-----------|----------|----------|
| **Runaway** (саморазгон) | Усиливающая петля без торможения — ресурсы растут экспоненциально | Игрок быстро становится слишком сильным, игра теряет вызов |
| **Deadlock** (тупик) | Цикл не может замкнуться — нет пути от выхода к входу | Игрок застревает без очевидного следующего действия |
| **Stall** (остановка) | Балансирующая петля слишком сильна — прогресс замедляется до нуля | Каждый шаг вперёд сопровождается шагом назад |
| **Brittleness** (хрупкость) | Система работает только в узком диапазоне параметров | Малейшее нарушение баланса рушит весь цикл |
| **Oscillation** (осцилляция) | Петли обратной связи конфликтуют — система «раскачивается» | Периодические перепады между слишком легко и слишком сложно |
| **Stagnation** (застой) | Нет источника нового — петля замкнута, но не даёт прогресса | Повторение одних и тех же действий без развития |
| **Triviality** (тривиальность) | Цикл не содержит осмысленного выбора | Оптимальная стратегия очевидна и единственна |

### Алгоритм

Алгоритм 3.2 состоит из 5 этапов:

1. **Классификация структурного типа** — определение Engine/Economy/Ecology
2. **Конструирование иерархии петель** — построение многоуровневой структуры
3. **Диагностика патологий** — проверка на 7 типов проблем
4. **Валидация** — формальная проверка устойчивости
5. **Генерация рекомендаций** — предложения по коррекции

## Блок 3: MDA Lab (/blocks/3)

### Назначение

Блок 3 реализует двойной MDA-процесс: цикл генерации (Reverse MDA: Эстетика → Динамика → Механики) и валидации (Classic MDA: Механики → Геймплей → Опыт). Это центральный блок для проектирования механик, который объединяет четыре режима работы: генеративный, аналитический, валидационный и структурный. Ключевой принцип: MDA — это двунаправленная модель, и оба прохода обеспечивают сходимость процесса.

### Четыре режима работы

#### 1. Reverse MDA (Генеративный режим)

Направление: **Эстетика → Динамика → Механики**

Используйте этот режим, когда вы знаете, какой опыт хотите создать, и вам нужно подобрать механики, которые его породят. Вы задаёте целевую эстетику (2–3 из 8 типов ЛеБланка), система определяет необходимые динамики и подбирает механики из MechanicsDB (127 механик в 15 группах).

**Как использовать**: укажите целевую эстетику, жанр и (опционально) уже выбранные механики. Система сгенерирует набор из 8–18 механик с полным покрытием всех целевых эстетик.

#### 2. Classic MDA (Аналитический режим)

Направление: **Механики → Геймплей → Опыт**

Используйте этот режим для проверки: порождают ли выбранные механики целевой опыт? Система моделирует взаимодействие механик через Machinations-симуляцию и определяет, какой опыт вероятнее всего возникнет у игрока, затем сравнивает с целевой эстетикой.

**Как использовать**: загрузите текущий набор механик. Система запустит симуляцию и покажет совпадение с целевой эстетикой (0–100%). Если совпадение ниже порога — предложит коррекции.

#### 3. Линзы Шелла (Валидационный режим)

8 приоритетных линз из 113 линз Шелла проверяют аспекты, которые MDA не охватывает: целостность (Тетрада, Единство, Резонанс), эмерджентность (Эмерджентность, Пространство действий), баланс (Треугольность, Доминантная стратегия), интерес (Кривая интереса, Свобода vs управляемость).

**Как использовать**: выберите релевантные линзы или запустите все 8 приоритетных. Для каждой линзы система оценит проект по шкале 0–1 и выявит проблемы.

#### 4. Матрица Бонда 4×3 (Структурный режим)

Расширенная матрица Бонда проверяет согласованность 4 элементов (Механика, История, Эстетика, Технология) на 3 уровнях (Фиксированный, Динамический, Культурный). Включает проверку на лудонарративный диссонанс — конфликт между тем, что игрок делает (механика), и тем, что история говорит (нарратив).

**Как использовать**: заполните матрицу или позвольте AI заполнить её из Project State. Система проверит горизонтальную (по строкам) и вертикальную (по столбцам) согласованность и выявит диссонансы.

### Что вы получаете

**MDAProfile** — полный профиль механик:

- Целевая эстетика и динамики
- Структурированный набор механик с группировкой по ролям
- Результаты Classic MDA-анализа (совпадение с целевой эстетикой, итерации сходимости)
- Валидация через линзы Шелла (8 оценок + выявленные проблемы)
- Матрица Бонда 4×3 с анализом согласованности и лудонарративным аудитом
- Machinations-модель для дальнейшего использования в Блоках 4–5

### Алгоритм

Алгоритм 3.3 состоит из 6 этапов:

1. **Reverse MDA: определение целевых динамик** — маппинг эстетика → динамики
2. **Reverse MDA: маппинг «Динамика → Механики»** — подбор механик с оптимизацией покрытия
3. **Сборка и оптимизация набора механик** — разрешение конфликтов, проверка синергий
4. **Classic MDA: аналитический проход** — моделирование геймплея, проверка сходимости
5. **Валидация через линзы Шелла** — 8 приоритетных линз
6. **Валидация через матрицу Бонда** — согласованность + лудонарративный анализ

## Блок 4: Баланс и симуляция (/blocks/4)

### Назначение

Блок 4 анализирует и балансирует игровые элементы — от оружия и персонажей до экономических ресурсов. Система поддерживает три модели баланса: транзитивную (сила пропорциональна стоимости), интранзитивную (камень-ножницы-бумага) и ситуативную (ценность зависит от контекста). Каждая модель дополняется Monte Carlo симуляцией и визуализацией экономики через Machinations.

### Пять вкладок

#### 1. Transitive Analysis (Транзитивный анализ)

Анализ элементов по принципу «стоимость ↔ мощность». Строит кривые cost/power для каждого элемента, выявляет переоценённые (дорого — слабо) и недооценённые (дёшево — сильно) элементы. Использует метод весов Шрайбера: AI оценивает значимость каждого атрибута элемента для данного жанра.

**Как использовать**: добавьте элементы с атрибутами (атака, защита, скорость и т.д.) и стоимостью. Укажите якорный элемент — эталон для сравнения.

#### 2. Payoff Matrix (Матрица выигрышей)

Интранзитивный баланс: строит матрицу «элемент A vs элемент B» с результатами противостояния. Определяет равновесие Нэша — ситуацию, при которой ни одному игроку не выгодно менять стратегию. Выявляет доминантные стратегии (один элемент побеждает все остальные).

**Как использовать**: введите 3+ элемента с характеристиками. Система автоматически построит матрицу и рассчитает равновесие.

#### 3. Simulation Charts (Симуляция)

Monte Carlo симуляция: 1000+ виртуальных сражений/встреч для проверки теоретического баланса на практике. Сравнивает формальный ранкинг (по cost/power) с эмпирическим (по результатам симуляции). Если ранкинги расходятся — система анализирует причину расхождения.

**Как использовать**: настройте количество итераций и параметры симуляции. Система визуализирует распределение побед и сравнит с теорией.

#### 4. Machinations Visualization (Визуализация экономики)

Графическое представление экономики игры в нотации Machinations (Адамс/Дорманс): пулы ресурсов, конвертеры, источники (faucet), стоки (drain), связи. Позволяет визуально оценить потоки ресурсов и выявить дисбалансы.

**Как использовать**: данные автоматически загружаются из MDA-профиля (Блок 3). Визуализацию можно редактировать, добавляя и удаляя узлы.

#### 5. Corrections (Коррекции)

AI-генерированные предложения по исправлению дисбалансов. Для каждой обнаруженной проблемы (переоценённый элемент, доминантная стратегия, расхождение симуляции с теорией) система предлагает 2–3 варианта коррекции с оценкой побочных эффектов.

**Как использовать**: после проведения анализа переключитесь на вкладку коррекций. Выберите подходящую коррекцию и примените.

### Что вы получаете

**BalanceResult** — полный результат балансировки:

- Кривые cost/power с выделением аномалий
- Матрица выигрышей и равновесие Нэша
- Результаты Monte Carlo симуляции (1000+ итераций)
- Machinations-визуализация экономики
- AI-коррекции с оценкой побочных эффектов

### Алгоритм

Алгоритм 3.4 реализует многоуровневый анализ: транзитивный (Шрайбер) → интранзитивный (Nash) → симулятивный (Monte Carlo) → корректирующий (AI).

## Блок 5: Экономика и прогрессия (/blocks/5)

### Назначение

Блок 5 — самый объёмный блок системы. Он состоит из двух больших разделов: **Прогрессия** (кривые роста, этапы, контент-план) и **Экономика** (ресурсы, Machinations-модель, симуляция, диагностика). Прогрессия отвечает за ощущение направленного роста, экономика — за устойчивость ресурсных потоков. Обе системы неразрывно связаны: прогрессия является результатом экономических потоков и одновременно их драйвером.

### Раздел «Прогрессия»

#### Вкладки

1. **Curves (Кривые)** — настройка математических кривых прогрессии: XP→Уровень (экспоненциальная, треугольная, линейная), Уровень→Мощность (линейная, полиномиальная, логистическая), Уровень→Стоимость, Кривая сложности. Каждая кривая имеет формулу и визуализацию.

2. **Tiers (Этапы)** — разбиение прогрессии на качественно различные этапы по модели D&D: Начальный (дефицит, обучение), Рост (инвестиции, расширение), Зрелость (стабильность, оптимизация), Эскалация (конкуренция, престиж). Каждый этап имеет свою доминантную механику и тип баланса.

3. **Content Plan (Контент-план)** — спецификация контента по уровням: количество и типы врагов, награды, разблокировки, ключевые события (боссы, новые области). Включает pacing-паттерн: «нарастание → пик → награда → передышка».

4. **Validation (Валидация)** — проверка прогрессии на 6 типов проблем: гринд (монотонные повторения), стены (резкие скачки сложности), пустые уровни (нет новых механик), runaway-прогрессия, разрыв билдов, эстетическое несоответствие.

5. **Macro Params (Макро-параметры)** — фундаментальные настройки: целевая длительность (часы), число уровней, тип прогрессии (линейная, экспоненциальная, S-кривая, прерывистая), модель замков/ключей (linear, metroidvania, dynamic, emergent).

### Раздел «Экономика»

#### Вкладки

1. **Resources (Ресурсы)** — определение всех ресурсов игры (валюты, материалы, XP, очки действий и т.д.) с классификацией: ядерные vs вспомогательные, возобновляемые vs невозобновляемые, с границами (min/max).

2. **Classification (Классификация)** — определение структурного типа экономики: Engine (усиливающие петли, один ресурс), Economy (конвертация ресурсов), Ecology (балансирующие петли). Включает определение источников (faucet) и стоков (drain) для каждого ресурса.

3. **Machinations** — визуальная модель экономики в нотации Адамса/Дорманса. Узлы: пулы (накопители), конвертеры (трансформации), источники (генерация), стоки (расход), связи (потоки). Модель можно редактировать интерактивно.

4. **Simulation (Симуляция)** — запуск Machinations-модели на 1000+ тиков для проверки устойчивости. Показывает: распределения ресурсов во времени, частоту действий, стабильность петель, соотношение faucet/drain.

5. **Diagnostics (Диагностика)** — проверка экономики на типичные проблемы: инфляция (faucet >> drain), дефляция (drain >> faucet), runaway (экспоненциальный рост), deadlock (нет источника ресурса), нестабильность (осцилляция).

### Что вы получаете

- **ProgressionProfile** — полная система прогрессии с кривыми, этапами, контент-планом и валидацией
- **EconomyProfile** — полная экономическая модель с ресурсами, Machinations-диаграммой, результатами симуляции и диагностикой

### Алгоритмы

- **Алгоритм 3.5** (Прогрессия): 4 основных этапа — макро-параметры → этапы → кривые → контент-план + 3 дополнительных (связь с экономикой, валидация, сборка)
- **Алгоритм 3.6** (Экономика): 7 этапов — ресурсы → классификация → Machinations → симуляция → диагностика → стоки → сборка

## Блок 6: GDD Generator (/blocks/6)

### Назначение

Блок 6 превращает всё проектное состояние (данные из Блоков 1–5) в структурированный Game Design Document (GDD). Ключевой принцип: документация — это проекция модели, а не отдельный артефакт. GDD не хранится как статический текст, а рендерится из Project State при каждом запросе. Изменение модели автоматически обновляет все зависимые разделы GDD, решая фундаментальную проблему рассинхронизации документации.

### Шесть вкладок

#### 1. Format Selector (Выбор формата)

8 форматов документации для разных стадий проекта и аудиторий:

| Формат | Объём | Аудитория | Когда использовать |
|--------|-------|-----------|-------------------|
| **One-Sheet** | 1 стр. | Все | Концепция, питчинг |
| **Ten-Pager** | 5–10 стр. | Продюсер, издатель | Решение о финансировании |
| **Treatment** | 5–6 стр. | Издатель, инвестор | Препродакшен |
| **Sketch Design** | 15–30 стр. | Команда | Прототипирование |
| **Full GDD** | 50–200+ стр. | Вся команда | Продакшен (38 секций Роджерса) |
| **Concept Doc** | 5–10 стр. | Команда, издатель | Препродакшен (системный подход) |
| **Narrative Bible** | 20–50 стр. | Сценаристы, художники | Нарративные игры |
| **Modular** | По требованию | По требованию | Любая стадия (13 независимых модулей) |

#### 2. Preview (Предпросмотр)

Полный предпросмотр сгенерированного GDD с навигацией по секциям. Автозаполняемые секции (50%) отображаются сразу, AI-генерируемые (34%) — с пометкой «требует проверки», ручные (16%) — со скелетом и подсказками.

#### 3. Section Editor (Редактор секций)

Построчный редактор для каждой секции GDD. Можно редактировать автозаполненные секции, проверять и корректировать AI-сгенерированные, заполнять ручные секции с подсказками. Каждая секция показывает источник данных и статус готовности.

#### 4. Consistency (Согласованность)

Проверка GDD на внутреннюю согласованность между секциями: Core Loop ↔ Механики, Прогрессия ↔ Баланс, Экономика ↔ Монетизация, Нарратив ↔ Механики (лудонарративный диссонанс), Целевая аудитория ↔ Контент. Несогласованности помечаются как critical/warning.

#### 5. Export (Экспорт)

Экспорт GDD в 4 формата: **Markdown** (.md), **HTML** (.html), **PDF** (.pdf), **DOCX** (.docx). Каждый формат сохраняет структуру документа, диаграммы и таблицы.

#### 6. Checklists (Чек-листы)

5 типов чек-листов валидации геймдизайна:

- **MDA** — проверка покрытия всех целевых эстетик механиками
- **Balance** — проверка транзитивного и интранзитивного баланса
- **Narrative** — проверка лудонарративной гармонии и агентивности игрока
- **Economy** — проверка устойчивости экономики и faucet/drain баланса
- **Shell's Lenses** — проверка через приоритетные линзы Шелла

### Алгоритмы

- **Алгоритм 3.7** (Генерация структуры GDD): 8 этапов — формат → маппинг данных → автозаполнение → AI-генерация → ручные секции → сшивка → согласованность → форматирование
- **Алгоритм 3.8** (Чек-листы валидации): 7 этапов — MDA-валидация → баланс → нарратив → экономика → линзы → агентивность → ремедиация

## Блок 7: AI-ассистент (/blocks/7)

### Назначение

Блок 7 — контекстно-осведомлённый AI-чатбот, который знает ваш проект и может помочь с любым аспектом геймдизайна. Ассистент основан на RAG (Retrieval-Augmented Generation) — он ищет релевантные фрагменты из 17 книг по геймдизайну и использует их как контекст для ответов. Это не просто чат-бот, а интеллектуальный помощник, который понимает контекст проекта и предлагает рекомендации.

### Три вкладки

#### 1. Чат (SSE Streaming)

Основной интерфейс общения с AI-ассистентом. Особенности:

- **Потоковая генерация (SSE)** — ответ появляется в реальном времени, по мере генерации токенов
- **Контекст проекта** — ассистент знает текущее состояние проекта (жанр, эстетика, механики, Core Loop) и учитывает его в ответах
- **Быстрые подсказки** — предустановленные вопросы: «Какие механики подходят для RPG?», «Проверь мой Core Loop на патологии», «Как сбалансировать экономику?», «Что такое лудонарративный диссонанс?»
- **Остановка генерации** — можно прервать ответ в любой момент
- **История чата** — все сообщения сохраняются и загружаются при повторном входе

**Как использовать**: просто напишите вопрос или выберите быструю подсказку. Ассистент ответит с учётом контекста вашего проекта.

#### 2. Подсказки (Suggestions)

Контекстные подсказки, специфичные для каждого блока. Выберите номер блока (1–8) и нажмите «Загрузить» — система проанализирует текущее состояние проекта относительно выбранного блока и предложит рекомендации с приоритетом (high/medium/low).

Подсказки бывают 4 типов действий:
- **generate** — предложить генерацию недостающих данных
- **validate** — предложить проверку существующих данных
- **fix** — предложить исправление обнаруженной проблемы
- **review** — обратить внимание на аспект, требующий ручной проверки

#### 3. Уведомления (Notifications)

Проактивные уведомления о проблемах, обнаруженных системой. В отличие от подсказок, уведомления инициируются самой системой, а не пользователем. Система регулярно проверяет Project State на наличие типичных проблем (runaway-экономика, несогласованность между блоками, пустые обязательные поля) и предупреждает о них.

Уведомления имеют 3 уровня серьёзности: **critical** (требует немедленного внимания), **warning** (рекомендуется исправить), **info** (информационное сообщение).

### Возможности AI-ассистента

- **RAG-поиск** по 17 книгам: Шелл, Зубек, Фуллертон, Адамс/Дорманс, Роджерс, Селлерс, Шрайбер и другие
- **Контекстная осведомлённость** — знает жанр, эстетику, механики, Core Loop, экономику проекта
- **Проактивное обнаружение проблем** — выявляет патологии до того, как они станут критичными
- **Цитирование источников** — каждая рекомендация обоснована теорией с указанием [Автор, Концепция]

### Спецификация

Блок реализует спецификацию 3.9 — 31 AI-промпт с трёхслойной архитектурой (System Prompt → Context Prompt → Task Prompt), маршрутизацией по моделям, кэшированием и fallback-цепочками.

## Блок 8: Интеграция GBE (/blocks/8)

### Назначение

Блок 8 — API Bridge для интеграции с **GDCombine** (Game Design Combine) — внешней платформой геймдизайна. Блок обеспечивает двусторонний обмен данными: экспорт проектного состояния из Gidede в GDCombine и импорт данных из GDCombine в Gidede. Это позволяет использовать обе системы совместно, leveraging сильные стороны каждой.

### Четыре вкладки

#### 1. Подключение (Connection)

Настройка подключения к GDCombine API. Поля:

- **GBE Base URL** — базовый URL инстанса GDCombine API
- **API Key** — ключ авторизации (необязателен в mock-режиме)
- **Кнопка «Проверить подключение»** — тест связи с GDCombine API, возвращает статус, версию GBE и задержку

После проверки подключения отображается: статус (подключено/не подключено), версия GBE, задержка (мс), режим (Mock/Production).

#### 2. Синхронизация (Sync)

Двусторонний обмен данными:

- **Экспорт в GBE** (Gidede → GDCombine) — передаёт текущее состояние проекта. Маппинг сущностей: OnePager → Blueprint, MDA-профиль → MDAModel, Balance → BalanceReport, Progression → ProgressionModel, Economy → EconomyModel
- **Импорт из GBE** (GDCombine → Gidede) — получает данные из GDCombine и обновляет проект. Обратный маппинг: Blueprint → Concept, MDAModel → MDA Profile и т.д.

Результат синхронизации показывает: Sync ID, направление, список синхронизированных и пропущенных компонентов, предупреждения, задержку.

#### 3. История (History)

Журнал всех операций синхронизации с полями: Sync ID, направление (Gidede → GBE / GBE → Gidede), количество компонентов, временная метка. Позволяет отследить все обмены данными.

#### 4. Настройки (Settings)

- **Направление синхронизации** — двусторонняя / только экспорт / только импорт
- **Включённые сущности** — выбор компонентов для синхронизации (Концепция, Core Loop, MDA-профиль, Балансировка, Прогрессия, Экономика)
- **Вебхуки** — настройка webhook-событий (blueprint.updated, diagram.changed, sync.requested, lint.completed) для автоматической синхронизации при изменениях в GDCombine

### Mock-режим

> ⚠️ **Важно**: Блок 8 в настоящее время работает в **mock-режиме** для целей разработки. Все операции выполняются с моковыми данными, реальное подключение к GDCombine API будет доступно после стабилизации GBE API (Фаза 4.E). Бейдж «MOCK-режим» отображается в интерфейсе блока.

### Реальная интеграция

После стабилизации GBE API (GDCombine) блок перейдёт в production-режим. Для этого потребуется:

1. Указать реальный GBE Base URL и API Key
2. Выбрать сущности для синхронизации
3. Настроить направление обмена
4. При необходимости — настроить вебхуки для автоматической синхронизации

## Сквозной пайплайн

### Как блоки связаны между собой

Gidede реализует **сквозной пайплайн** проектирования, в котором данные автоматически передаются от блока к блоку:

```
Блок 1 (Концепция)
    ↓ OnePager + эстетика + механики
Блок 2 (Core Loop)
    ↓ CoreLoopProfile + иерархия + диагностика
Блок 3 (MDA Lab)
    ↓ MDAProfile + валидация + Machinations
Блок 4 (Баланс)
    ↓ BalanceResult + кривые + коррекции
Блок 5 (Экономика/Прогрессия)
    ↓ ProgressionProfile + EconomyProfile
Блок 6 (GDD Generator)
    ↓ GDD + чек-листы + экспорт

Блок 7 (AI-ассистент) ← доступен на любом этапе
Блок 8 (Интеграция GBE) ← внешний обмен данными
```

### Автоматический поток данных

Результат каждого блока становится входом для следующего:

- **Блок 1 → Блок 2**: OnePager (концепция), эстетический профиль, набор механик, предварительный Core Loop
- **Блок 2 → Блок 3**: CoreLoopProfile (иерархия петель, структурный тип, диагностика патологий)
- **Блок 3 → Блок 4**: MDAProfile (набор механик, Machinations-модель, целевая эстетика)
- **Блок 4 → Блок 5**: BalanceResult (сбалансированные элементы, кривые cost/power)
- **Блок 5 → Блок 6**: ProgressionProfile + EconomyProfile (кривые, контент-план, ресурсы)

### Каскад устаревания (Stale Cascade)

При изменении данных в раннем блоке все зависимые блоки помечаются как **устаревшие (stale)**:

- Изменение концепции (Блок 1) → stale: блоки 2, 3, 4, 5, 6
- Изменение Core Loop (Блок 2) → stale: блоки 3, 4, 5, 6
- Изменение MDA (Блок 3) → stale: блоки 4, 5, 6
- Изменение баланса (Блок 4) → stale: блоки 5, 6
- Изменение экономики/прогрессии (Блок 5) → stale: блок 6

Это гарантирует, что GDD всегда отражает актуальное проектное состояние.

### Полный пайплайн

В Блоке 1 доступна кнопка **«Запустить пайплайн 1→2→3»**, которая последовательно выполняет генерацию концепции, проектирование Core Loop и MDA-анализ за один запуск. Это удобный способ быстро получить результаты первых трёх блоков.

## Часто задаваемые вопросы

### Можно ли использовать блоки не по порядку?

Технически — да, вы можете открыть любой блок напрямую. Однако большинство блоков требуют входных данных от предыдущих. Например, Блок 3 (MDA Lab) не сможет подобрать механики без целевой эстетики из Блока 1. Рекомендуется начинать с Блока 1 и двигаться последовательно.

### Что такое «Reverse MDA» и зачем он нужен?

Reverse MDA — это подход к проектированию, при котором вы начинаете с целевого опыта игрока (эстетика по ЛеБланку) и выводите из него механики. Это отличается от обычного подхода, когда дизайнеры начинают с механик и надеются, что получится интересный опыт. Reverse MDA целенаправленно конструирует игру, чьи механики гарантированно порождают нужный опыт.

### Могу ли я редактировать результаты генерации?

Да! Все автозаполненные и AI-сгенерированные результаты можно редактировать. В Блоке 6 (GDD Generator) есть секционный редактор для точечной правки. Кроме того, вы можете вернуться к любому предыдущему блоку и изменить входные данные — система автоматически пометит зависимые блоки как устаревшие.

### Что делать, если AI выдаёт некачественный результат?

Система использует fallback-цепочки: если основная AI-модель не справляется, автоматически пробуется запасная. Если и она не помогает — применяется детерминированная заглушка. Вы также можете повторить генерацию — AI-результаты вариативны, и повторный запрос может дать лучший результат. Для критичных решений всегда сверяйтесь с теорией (цитаты в ответах AI-ассистента).

### Сколько данных нужно для начала работы?

Минимум — одно предложение с описанием идеи в Блоке 1. Система автоматически заполнит недостающие параметры: определит жанр, подберёт эстетику по умолчанию, предложит механики. Чем больше данных вы предоставите (референтные игры, целевая аудитория, бюджет), тем точнее будет результат.

### Что означает «MOCK-режим» в Блоке 8?

MOCK-режим означает, что Блок 8 (Интеграция GBE) работает с тестовыми данными, а не с реальным API GDCombine. Это необходимо, поскольку GDCombine API ещё находится в разработке. После стабилизации GBE API блок перейдёт в production-режим с реальным обменом данными. Все остальные блоки (1–7) работают полностью функционально.
